## 2. 现状核实与「不建闸门」的结论

### 2.1 三条已核实事实（截至今日本机代码）

1. **容器写路径恒写 `dist_class='public'` / `state='active'`，没有「待授权」状态。** 容器落库 `UpsertSegmentSubmission` 的 `INSERT INTO items(...)` 中 `VALUES(?,?,?,?,?,?,?,'public','active',?,?,?)` 两列写死字面量（`internal/store/submission.go:141-147`，字面量 L141-142），`ON CONFLICT` 不写 `state` / `dist_class`（L140 注释）；`article` / `quiz` 分支 `UpsertSubmission` 同形（`submission.go:64-70`，字面量 L69-70）。⇒ **验签通过即 `active` 生效，没有「待授权」态可落**。
2. **`POST /v1/submit` 类型分支无任何「待授权」分支。** `handleSubmitPost` 的 `switch req.Type`（约 `internal/httpapi/submit.go:198-235`）只做形态校验，通过即落库（L317-347），**全分支无授权 / 票数判定**（`tag` 分支的 `tag_not_governor` 是 `#37` 打标资格，与创建授权无关）。⇒ **服务端连「未授权」落点都没有**。
3. **用户原话的人数门槛（<10 / ≥10）在本系统无对应实现。** 名册人数上限是 `internal/store/contributor.go:14-16` 的 **`RosterTopN = 10`**（前 10 名即治理者），由 `deriveRoster`（`contributor.go:62-86`）实时派生、不落表；系统里唯一按人数挂门槛的是 `#27` 提案的**他人条目**改写 / 下架（`remove` 3 票、`edit` / `revive` 2 票，名册不足即挂起——`approval-governance-design.md:101-105,147-161`），管的是**他人的已有条目**、**不是创建时授权**。⇒ 原话「<10 人自授权」无落点（写路径恒 `active`）、「≥10 人投票创建」无接口；`10` 恰等于 `RosterTopN` 但**语义不同**（名册截断长度 ≠ 治理者总票池）。

### 2.2 立论：**不建闸门**，只做可见性

三条合起来：**「未授权」状态在本系统根本不存在 ⇒ 无闸门可建**。若强行新造「创建需授权」状态机，须同时改 `store` 落库、`httpapi` 分支、`#25` 占用口径与 `#27` 门槛语义，是**推翻既有契约**的改法（§2.3）。故本册**只做可见性**：让作者保存后立刻在任何浏览面看到自己创建的内容及状态，满足原话诉求③。

### 2.3 与总纲 / `#27` 的核对（**经核对无缺口，不改**）

- 总纲已明确「创建不需要审批」：guest 路径「**无需注册、无需等待节点审批**」（`distributed-learning-design.md:270`）；「`dist_class` 是可见性分类，**不是授权**」（L381）；「**无 `license` 表**」（L533）。
- `#27` 定位是**他人条目**的 `remove` / `edit` / `revive`，且明确「`author_id == 提案人` 的条目一律拒绝并指向 `POST /v1/submit`——**作者改自己的内容永远不需要审批**」（`approval-governance-design.md:121,437`），与「创建时无闸门」自洽。
- **回填结论**：总纲与 `#27` **无缺口，不改**（§7）。

## 3. 契约：台账可见性视图

### 3.1 「我创建的」区的结构

- **落点**：`apps/mobile/src/pages/course/course.vue`（模板 L1-50、`load()` L81-117、导航 L157-167）。
- **位置**：课程页**顶部**（标题栏 + 搜索框之下），在「分类分组 / 未归类 / 独立内容」诸区**之上**。
- **数据源**：`LocalRepo.listSubmissions()`（不带 `state` 取全部，`repo.ts:86-96,523-529`），含三态；**刷新**：课程页 `onShow` 触发 `load()`（`course.vue:169-171`）。
- **每行**：`type` 中文标签（课程 / 课时 / 文章 / 题库）· `title` · 状态（§3.2）；按 `queued_at ASC`（既有排序）展示。
- **载体范围**：台账 `type` 取值集 `article|quiz|tag|course|lesson`（`types.ts:113`）。本区展示 **`course` / `lesson` / `article` / `quiz`**；**`tag` 行不列入**（归标签页，§4 边界 3）。

### 3.2 每行状态与文案（复用 `myitems.vue:7-47` 口径，不另造词汇）

| 台账 `state` | 展示 | 说明 |
|---|---|---|
| `pending` | **待补发** | 断网 / 429 / 5xx（`submit.ts:310-330`），联网后自动补发 |
| `failed` | **失败** + `reason` | 其余 4xx 永久失败（单向），显示 `reason`（错误码映射后的中文） |
| `sent` | **已同步**（或按 §3.4 折叠） | 已送达节点 |

`reason` 为空串时不显示原因行；`failed` 行按 `myitems.vue:42` 红字样式展示。

### 3.3 点开用台账行集就地渲染（不碰包表、不碰节点）

- **原则**：详情**只吃台账行**，不读 `repo.getItem` / `listSegments` / `findBlobPathByItem`，**不发起任何网络请求**。
- **桥（纯函数 `core/my-created.ts`）**：
  - `course` / `lesson`：解析 `segmentsJson`（`[{seq,kind,text}]`）为行集，复用 `core/container-view.ts` 的 `attrsOf` / `digestOf` / `childrenRowsOf` 与 `core/course-edit.ts` 的 `ContainerForm` 字段映射（`loadContainerForm` L117-132），产出同构视图模型——只换数据源为台账行集，**不写包表**。
  - `article`：取台账 `bodyMd`；`quiz`：取 `questionJson`。二者已是详情页所需全量源。
- **跳转**：点行 → 走既有详情页路由并带**台账来源标志** `&from=ledger`（路由形态照 `course.vue:157-167`）；详情页 `onLoad` 见该标志即改从 `repo.getSubmission(row.itemId)` 取数渲染。**缺行退化**：`from=ledger` 而台账无该行（已删）⇒ 回落各页既有错误 / 空态提示，**不抛白屏**。
- **正文渲染**：`article` / `lesson` 正文按 `#44` 管线渲染；台账存源文本（`#29 §5.1`），渲染是只读派生。

### 3.4 去重口径（「我创建的」区 vs「课程」区）

同一 `item_id` 既在包表（`items`，已同步）又在台账时，「课程」区（读包表）与本区（读台账）会**重复**，定死如下：

| 台账行 | 包表是否已有该 `item_id` | 本区处理 |
|---|---|---|
| `pending` | 任意 | **列出**（包表一定没有它） |
| `failed` | 任意 | **列出**（附 `reason`）——失败项**只此一处**可见 |
| `sent` | **已有** | **不列出**（已由「课程 / 未归类 / 独立内容」诸区承载） |
| `sent` | **没有** | **列出**，标「已同步」——包表暂无它（尚未拉包 / 已被下沉），此处是唯一可见面 |

- **判据**：`repo.getItem(itemId) !== null`（`repo.ts:23`）。
- **取舍理由**：`sent` 且包表已有 ⇒ 课程区已完整承载，再列一遍只是同一数据的第二个渲染面（与 `#40 §5.1` 同取舍：**同一份数据不做两个渲染面**）；`pending` / `failed` 不在包表、只能在此看到，故一律列出（F2 / F8 落点）。「已同步」行**列出 + 标记**而非折叠，以免丢掉 `item_id` 与标题、弱化可见性。

### 3.5 表结构零改动（登记）

本册**不改** `my_submissions` DDL 与 `LocalRepo` 六方法（`repo.ts:126-131,511-553,648-667`；`types.ts:109-127`）。本区是新加的**只读消费点**，不是新存储形态——「台账第三个只读用途」的准确含义（§7 已在 `#29` 登记）。

## 4. 已知边界（登记，不在本册修）

1. **用户原话的授权规则无对应实现**：原话②「…<10 人自授权 / ≥10 人投票」在本系统现状下**无对应实现**——创建内容恒为 `active`、无「待授权」态（§2.1 第 1、2 条）；按人数挂门槛的只有 `#27` 的他人条目改写 / 下架提案（§2.1 第 3 条）。原话「10」与 `RosterTopN = 10` **数值巧合而语义无关**。本册不据此新造任何闸门。
2. **台账是本地投影**（`#29 §11.1`）：换机 / 重装后本区为空。
3. **`tag` 行不列入本区**：标签可见性归标签页与「我的条目」页（`#37`）。
4. **下沉条目的台账残留**：本区按台账 `state` 展示，不读节点真实状态；若我的条目经 `#27` `remove` 被下沉，台账行仍是 `sent` → 可能被列为「已同步」标记行，提示语仅说明「本机还没有」，**不断言「已下沉」**。
5. **`sent` 且包表已有的行不可见**：想看「我投过的全部」应去「我的条目」页——本区是**浏览面**。

## 5. 验收

- **AC 1**（F2 / F8 主验收）：新建课程 / 课时 / 文章 / 题库，**保存后立刻**返回课程页，本区可见该条目；`pending`（断网）与 `failed`（4xx）**都**可见并带正确状态文案。
- **AC 2**：`pending` 标「待补发」、`failed` 标「失败」且显示 `reason`、`sent` 且包表已有 → **不列出**、`sent` 且包表没有 → 标「已同步」并列出。
- **AC 3**：点开本区某条 → 详情页**用台账行集渲染**（课程 / 课时取 `segments_json`、文章取 `body_md`、题库取 `question_json`）；**包表尚无该条目**时仍能打开渲染，**全程无网络请求**。
- **AC 4**：去重无重复——同一 `item_id` 不在「课程」区与本区同时出现；`pending` / `failed` 行不产生冲突渲染。
- **AC 5**：F2 / F8 的「文章页 / 课程页看不到内容」被消除——新建文章 / 题库 / 课程 / 课时保存后均可从本区进入并看到内容。
- **AC 6**：`my_submissions` 表与 `LocalRepo` 六方法零改动；`items` / `segments` / `blobs` 与 `core/sync.ts` 零改动；**零新增 / 修改 HTTP 接口**（`git diff` 佐证）。
- **AC 7**：门禁——Go `build`/`vet`/`test`、mobile `npx vitest run`（**不少于 23 文件 / 230 用例**）/ `tsc --noEmit` / `build:h5`、`scripts/acceptance-d.ps1`、发布前硬检查（模板 `.value` 扫描无输出）全通过。
- **AC 8**：真机——新建课程（断网）→ 本区立刻可见（待补发）→ 联网后转「已同步」；新建内容（有网）→ 立刻可见且能点开看到正文。

## 8. 风险点

1. **被误读为「该建闸门只是没建」**：原话带「治理规则」措辞，易被当作缺失功能重立项。防线是 §2.1 三条带行号事实 + §4 边界 1；若后续要求「创建时授权」，必须先推翻 `#25` / `#27` / 总纲的既有契约。
2. **台账投影时效（§4 边界 2）**：换机 / 重装后本区为空，用户可能误以为「内容丢了」。本册不解决（`#29 §11.1`）。
3. **与 `#49` 同页改动的顺序耦合**：批次编排已定 **F6 先于 F7**（`#45 §3`），本册在 `#49` 落地后做，避免同一文件反复重构。
4. **去重判据的性能**：对每个 `sent` 行做 `repo.getItem`（§3.4）——本地条目量 1e3 量级，逐条查询可接受；不做批量优化。
5. **点开渲染的缺行退化（§3.3）**：`from=ledger` 而台账行已删须**优雅退化**，不得白屏（AC 3 判据）。

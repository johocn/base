## 3. L2 圈子自治

### 3.1 圈子形态与数据隔离

**数据隔离**：圈子继续独占 `group/<32hex>` 的 `target_id` 命名空间与 `group.v1` 事件类型；圈内事件与课程 / 文章 / 讨论 / 评论流**零交叉**（既有事实，本册不改）。**权限隔离**：L2 只管圈内（名单、密钥、圈名、消息），L1 只管非圈子内容，**两层互不越界**。

| 形态 | `encrypted` | 正文 | 读权 | 加入方式 |
|---|---|---|---|---|
| **开放圈** | `0` | 明文（同 ①类） | **匿名可读** | **自助自加入**（已登记身份签名即可，无需治者放行） |
| **封闭圈** | `1` | AEAD 密文 | **成员签名读权**，非成员 `404` | 邀请码带密钥（任一在册成员或治者可签发） |

形态**建圈时定死，不允许切换**：公开 → 封闭的历史明文不可回收、封闭 → 开放会产出「旧密文新人不可解」的混合态，两边都是语义黑洞。存量小组一律 `encrypted = 1`（语义不变）。

### 3.2 治理人席位阶梯

**席位总数**（`m` = 当前成员数）：

```
k(m) = 1                                        , m ≤ 10
k(m) = min(10, 3 + floor((m - 11) / 10))        , m > 10
```

| m | ≤10 | 11–20 | 21–30 | 31–40 | 41–50 | 51–60 | 61–70 | 71–80 | ≥81 |
|---|---|---|---|---|---|---|---|---|---|
| k | 1 | 3 | 4 | 5 | 6 | 7 | 8 | 9 | **10（封顶）** |

**席位构成**：**创建者永久占 1 席**（与贡献度无关、不因排名下滑失位）+ 其余 `k − 1` 席按**圈内贡献度排名**取（§3.3）。创建者本身若已在排名内也不重复占席（取第 2…k 名）。不设创建者之外的特权。

### 3.3 圈内贡献度排名算法

**输入面**：本节点已验签的 `group.v1` `action=msg` 事件集合。封闭圈为密文事件、开放圈为明文事件，**两者口径相同**——只数事件条数，不看正文。实现为**只读派生函数、不落表**。

1. **去重**：按 `event_id` 去重，重复事件只计一次。
2. **计数**：`count(actor) = 该 actor 去重后的发言条数`。
3. **防刷**：同一 actor 在**任意滚动 24h 窗口**内最多计 20 条（超出部分不计；窗口边界取整到秒）。
4. **准入过滤**：只统计 `actor ∈ 当前成员名单` 的事件；已移出者的历史发言不计入排名（事件仍留库）。
5. **排序键**：`count` 降序，**同分按 `actor_id` 的 hex 字典序升序**——这条是各节点算出同一名次的前提。
6. **席位归属**：创建者永久 1 席；其余取排序后前 `k − 1` 名且不含创建者。
7. **边界**：第 `k` 名与第 `k+1` 名同分时取 `actor_id` 字典序小者，**不留「并列」状态**（避免节点间歧义）。
8. **快照水位**：名次判定附带 `(roster_rev, event_watermark)`；`roster_rev` = 成员变更计数，`event_watermark` = 该圈事件 `event_id` 集合排序拼接后取 `sha256` 前 16 hex。门槛与票权一律按快照水位复算，**不按当前实时复算**。
9. **不可判定**：事件集合未复制齐（水位缺口）时返回「不可判定」，**不猜名次**（与 #27「名册不足门槛即挂起」同族）。

**验收断言样例**：5 名成员、发言 `A=30, B=20, C=20, D=5, E=0` ⇒ 名次必须为 `A(按防刷截断为 20) → B → C → D → E`（B、C 同分按 `actor_id` 升序）；把 A 的同一 `event_id` 重放 100 次，名次**不得变化**。

### 3.4 决议规则与门槛

**动作分档**：

| 档 | 动作 | 门槛 |
|---|---|---|
| 低风险（直权） | 改名、主动轮换密钥、自己退出 | 任一治者 1 签 |
| 低风险（在册即可） | 签发邀请码拉人进圈（封闭圈） | 任一**在册成员**，无需签名门槛（§3.6） |
| 重大 | **移出成员** | 治者赞成 ≥ `⌈2k/3⌉`（k = 1 时自动为 1 签） |
| 最重大 | **解散圈子** | **成员**赞成 ≥ `⌊m/3⌋ + 1`（必须超过 1/3），**不叠加治者门槛** |

* 口径按 2026-09-29 定稿：移出 = 治者 2/3；解散 = 成员 1/3。解散**不设治者分项**——治者对解散**没有否决权**，这是明确取舍（§7 第 5 条）；两个档位落在不同维度上，不存在单调性比较。
* **算例**：`m = 11` ⇒ 解散需 `⌊11/3⌋+1 = 4` 名成员签名（不要求其中含治者）；`m = 200` ⇒ 67 名成员签名；`m = 3` ⇒ 2 名成员签名。
* **明确代价**：大圈子的解散需收集数十名成员签名，可能长期挂起——这是「重大问题需够人」的应有之义，挂起态必须在界面原位说明，禁止静默。

**生效方式：多签生效，节点不数票。** 节点不解密圈内内容，因此**不能**由节点数票判定门槛。做法：圈内提案与讨论走**密文事件**（治者持当前 epoch 密钥可解），而**生效**由 `action=roster` 事件承载并要求携带 `sigs[]`；节点只验三件事——**签名者都属于该动作要求的集合**（移出成员 = 圈内治者；解散圈子 = 圈内成员）**∧ 签名数 ≥ 对应门槛 ∧ `epoch` 严格递增**。既保住「节点不解圈内语义」红线，又让门槛可确定性校验，且不改签名算法。

### 3.5 密钥生命周期与轮换信封链

* 组密钥 32 字节随机，**一 epoch 一把**；**成员集合任一变更即 bump `epoch`**（加入 / 移出 / 重新加入）。
* **加入**：邀请码携带当前 epoch 密钥 + **历史 epoch 密钥列表**（新人能解入圈前历史）；历史上限 **32 个 epoch**（每 epoch 64 hex，约 2KB），更早历史不可读——明确代价。
* **移出**：轮换后**不为被移出者生成信封** ⇒ 其读不到后续（界面必须原位提示，不静默跳过）。
* **轮换分发（对称信封链，零新算法）**：新 epoch 密钥用**旧 epoch 密钥**逐成员 AEAD 加密成信封，随 `action=roster` 事件的 `envelopes[]` 进节点；成员读到后用本地旧密钥解开、写入 `group_keys`。信封是密文，**节点仍不持有任何密钥**。离线跨越多个 epoch 的成员按「其最后持有的 epoch」逐层解链。
* 本册**不做**逐人非对称信封与前向安全（需 X25519，超出「零新算法」口径）。

### 3.6 准入：开放圈自加入 / 封闭圈邀请码

* **开放圈**：非成员以已登记身份签发自加入事件（`action=roster` 的 `join` 子类型，签名者 = 自己），节点校验「圈为开放 ∧ 申请人是已登记身份」后写入名单，**无需治者放行**；开放圈不加密，入圈即可读。
* **封闭圈**：邀请码 = 当前 epoch 密钥 + 历史密钥包 + 圈元信息 + 签发者签名（签名者可为**任一在册成员或治者**，不再是创建者独有），可**离线自验**；`decodeInvite` 的新字段（`historyKeys` / `encrypted` / `rosterRev`）**全部可选**，保证老客户端不拒收（G6）。
* 「开放自加入」与「加密」在**没有非对称加密**的前提下不可兼得（G5），故本册把二者解耦为两种形态——这是明确取舍，不是遗漏。

### 3.7 读权与跨节点复制

* `GET /v1/group/{group_id}` 按形态分支：**开放圈**匿名可读；**封闭圈**需成员签名读权（客户端 Ed25519 签名挑战，体例复用 S1 既有 reqsig 中间件），节点查本地 roster 决定 `200 / 404`；**非成员一律 404，不泄露存在性**。
* 圈内事件与 roster 的跨节点复制改走**对端专用通道**（现有 `POST /v1/event-sync` 即对端专用，体例同 #5「公开 / 对端路由隔离」+ 反熵），缓存节点据此持有副本并能逐请求鉴权——**手机端连接拓扑不变**（nginx → 缓存节点）。
* `GET /v1/blob/{cid}` 密文块**保持可取**（内容寻址、被 ①类公开内容复用）；`cid` 只出现在圈内索引里，对非成员不可达 ⇒ 等价隔离。这是**明确记录在案的取舍**：不做逐块鉴权（会破坏块缓存与复用）。
* 节点侧**新增的仍是密文字节**（`envelopes`、圈内密文正文），不新增任何密钥语义。

### 3.8 节点侧状态与校验

`groups` 表扩展（列不删、**不 bump `schema_version`**）：新增 `encrypted`（0/1，存量默认 1）、`roster_rev`（成员变更计数，单调 +1）、`key_envelopes`（密文 JSON 文本）。写权校验由「owner 锁」放宽为**「写者 ∈ 圈内治者名单 ∧ 门槛签数达标 ∧ `epoch` / `roster_rev` 严格递增」**；多签签名域新增常量 **`base/group-roster-v2`**，**旧单签事件仍按旧域接受**（兼容存量）。

## 4. L1 全局治理一致性

### 4.1 缺口定位

名册派生规则本身已是确定性的（排行 + 门槛），其输入是**内容数据包**——导入同一包的各节点算出的名册本就相同（#24 AC 9 正是验这个）。真正不同步的是**提案与投票的结论**：它们只在本地生效，靠「导出 / 导入包」间接传播（#28 AC 13）。故重规划落在**把治理动作事件化**，让结论不依赖包搬运即可收敛。

### 4.2 `govern.v1` 事件

与 `comment.v1` / `group.v1` 并列注册（`eventTypeRegistry` 加一行 + 分流分支）：

* `action=proposal`：`proposal_id`、`target_item_id`、`verb`（`remove` / `edit` / `revive`）、`content_hash`（乐观锁）、提案人签名、可选密文正文。
* `action=vote`：`proposal_id`、`choice`、投票人签名。

签名域新增常量 **`base/govern-v1`**（沿用 `base/*-v1` 体例，与 `base/author-v1` 同族），并**产出契约向量**。复制链路**零改动**（G3：反熵不按 type 过滤）；节点侧新增**接收侧投影还原**（体例同 #31 的 `applySyncedGroupEvent`）。

### 4.3 确定性判定与收敛

* **票权按提案快照水位判定，不按实时名册**：提案建立时记录名册水位 `(content_version, revoked_rev)`（现有列，**零新状态**），投票权以该水位下的名册为准。这**修正 #27 的「票实时复判」**——实时复判会让不同节点因名册差异得出不同结论。
* **并发收敛**：同一 `proposal_id` 的并发提案取 `(created_at, event_id)` 字典序首个；票按 `(proposal_id, voter)` 去重取最早。
* **门槛分档沿用 #27**（`remove` 3 票、`edit` / `revive` 2 票）；生效后的 `content_version` 递增仍走现有 `NextContentVersion`。
* **派生而非决议**：生效是「确定性派生」的结果，不是某个节点「决定」的；任一节点从同一事件集合导出同一结论。

### 4.4 兼容与迁移

* `govern_proposals` / `govern_votes` 改为**本地物化视图**：加一列可空 `source_event_id`（**不删列、不 bump `schema_version`**），新事件投影写入，存量本地提案仍可读。
* 老客户端路径 `POST /v1/proposal` / `POST /v1/proposal/{id}/vote` **保留并双写**产出 `govern.v1` 事件 ⇒ 不强制升级。
* 节点侧不新增配置项。

## 5. 改动面清单

**节点侧（Go）**：`groups` 表三列与写权放宽、多签校验（`base/group-roster-v2`）、`group.v1` 的 `roster` 扩展 `join` / `leave` / `remove` / `rename` / `rotate` 子类型 + `sigs[]` / `envelopes[]`；`GET /v1/group/{group_id}` 按 `encrypted` 分支加签名读权；圈内事件跨节点复制走对端通道；圈内贡献度只读派生函数；`govern.v1` 注册 + 投影还原 + 水位记录；`govern_*` 两表加 `source_event_id` 与双写。

**客户端侧（uni-app）**：`core/group.ts` 的密钥生命周期（变更即轮换 + 历史密钥包）、信封链解密、多签生成与校验、双形态与自加入、邀请码可选新字段；圈子列表页形态标记与建圈选型；会话页治者面板（成员管理 / 改名 / 轮换 / 解散提案）与席位、贡献度展示；`core/govern*.ts` 消费事件化结论与水位展示。

**零新增**：不新增原生插件、不新增 KEK 种类、不新增 blob 上传面、不引入非对称加密、不改内容包规范 v1。

## 6. 错误码与提示口径（新增）

| 错误码 | 触发 | 提示要求 |
|---|---|---|
| `group_read_denied` | 非成员读封闭圈 | 对外一律 `404`，**不得**回 403 泄露存在性 |
| `group_invite_required` | 向封闭圈自加入 | 原位提示「该圈子仅接受邀请码加入」 |
| `group_roster_quorum_missing` | 多签数不足门槛 | 原位提示「需 N 名签名（移出=治理者 / 解散=成员），当前 M 名」 |
| `group_roster_epoch_stale` | `epoch` 未递增 | 提示「密钥已轮换，请先同步圈内状态」 |
| `group_decrypt_failed`（客户端） | 被移出 / 密钥不匹配 | **原位提示，禁止静默跳过**（沿用 #9 §5.3 口径） |
| `govern_event_conflict` | 同 `proposal_id` 并发冲突 | 按 §4.3 收敛，界面展示被选中的那一条 |

## 7. 红线与代价（记录在案）

1. **节点永不持有组密钥**、不解密封闭圈正文与圈内决议正文（总纲 §12 第 9 条）。
2. **块保持可取**：`GET /v1/blob/{cid}` 不做逐块鉴权（等价隔离，见 §3.7）。
3. **开放圈不加密**：开放即公开，属形态语义，不是加密强度不足。
4. **历史上限 32 个 epoch**：更早历史新人不可读。
5. **解散没有治者否决权**：解散门槛只看成员签名数（`⌊m/3⌋+1`），治者不构成否决项；且 **`m ≤ 3` 时 1–2 名成员签名即可解散**（§3.4 算例）——小圈子最脆弱，属定稿口径的代价。大圈子解散可能长期挂起，需原位说明。
6. **不做形态切换**：开放 ↔ 封闭不可逆切换会产出语义黑洞（§3.1）。
7. **L1 票权按快照水位**：名册中途变化不改判——这是收敛的代价，也是可解释性的收益。

## 8. 验收（AC）

| # | 验收 | 判定 |
|---|---|---|
| AC 1 | 隔离与形态 | 封闭圈非成员 `GET /v1/group/{id}` → **404**；开放圈匿名 200 且自加入后立即可读 |
| AC 2 | 席位阶梯 | `m = 10 → 1`、`11 → 3`、`20 → 3`、`21 → 4`、`41 → 6`、`81 → 10`、`200 → 10`，单测全覆盖 |
| AC 3 | 贡献度排名 | §3.3 断言样例逐条通过；`event_id` 重放 100 次名次不变；同分按 `actor_id` 升序 |
| AC 4 | 轮换与信封链 | 成员变更后 `epoch` +1；其余成员**不粘贴续期码**自动获新钥；新成员能解入圈前历史 |
| AC 5 | 移出即失读 | 被移出者新消息解密失败，且界面**原位提示**原文可核对（不静默） |
| AC 6 | 移出成员门槛 | 治者签名数 < `⌈2k/3⌉` 时节点拒写（`group_roster_quorum_missing`）；`k = 1` 时 1 签即可 |
| AC 7 | 解散门槛 | 成员签名数 < `⌊m/3⌋+1` 时节点拒写，且**不校验治者签名数**；算例 `m = 11 → 4`、`m = 200 → 67`、`m = 3 → 2` 通过 |
| AC 8 | 开放圈明文 | 开放圈消息在节点库与块目录为**明文**（形态语义），非成员亦可读 |
| AC 9 | 封闭圈不可读 | 节点 `data/base.db`（含 wal）与 `data/blobs/*` 无封闭圈明文 |
| AC 10 | 跨节点复制 | 圈内事件经对端通道到达缓存节点，成员从缓存节点（非源节点）读到并解密成功 |
| AC 11 | L1 收敛 | 两台节点**只靠反熵**（不做包导出 / 导入）收敛到同一提案结论（提案、票集合、生效状态逐字一致） |
| AC 12 | L1 票权水位 | 提案建立后名册变化，结论**不改判**（按快照水位复算稳定） |
| AC 13 | 兼容 | 存量 `groups` 行默认 `encrypted = 1`；存量邀请码可用；`0.9.3` 客户端不因新字段报错 |

## 9. 分期与发布

* **Phase 1（L2 圈子自治）**：列与形态、席位与贡献度派生、多签门槛、密钥轮换与信封链、读权分支与对端复制、客户端双形态与治者面板。
* **Phase 2（L1 全局治理一致性）**：`govern.v1` 注册与投影、水位口径、双写兼容、客户端消费。
* 版本从 **`0.10.0` / `14`** 起；两阶段各自完整走**发布四步**（云打包 → 上传 `/opt/appdl` → 落地页整页重写 → `based release` 签发落 `/opt/base-cache/data/release.json`），节点侧有用户可见改动时**必须同时交叉编译部署两个节点二进制**。

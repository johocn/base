## 1. 目标与判定

| # | 目标 | 判定 |
|---|---|---|
| 1 | 两台设备不联网也能组队 | A 建组出邀请码 → B 粘码入组 → 双方用同一组密钥互读消息（§3.3、AC 1） |
| 2 | 小组内容对节点是**不透明密文** | 节点库与块目录原始字节中不出现小组消息明文（§4.1、AC 3） |
| 3 | 组成员能跨节点取到消息 | A 节点发言 → B 节点匿名拉索引 + 取密文块 → 解密成功（§4.3、AC 4） |
| 4 | 名单有唯一权威且不可伪造 | 非创建者签的 `roster` 事件被拒；`epoch` 不递增的 `roster` 被拒（§4.2、AC 5 / AC 6） |
| 5 | 移出成员后新消息对其不可读 | 轮换后新消息用新 epoch 密钥；被移出者解密失败并以明文提示引导（§5.3、AC 7） |
| 6 | 断网发言不丢 | 复用 `comment_out` 入队 → 联网补发仅一条（§5.4、AC 8） |

**非目标**：不做成员准入读控制（索引匿名可读，见 §4.3 的代价）、不做前向安全、不做密钥托管、不做群主转让。

## 3. 契约

### 3.1 标识

| 项 | 定案 | 理由 |
|---|---|---|
| `group_id` | 客户端生成 **16 hex 随机**（与 `event_id` 同形） | 与「`event_id` 由客户端自带、节点只登记不签发」一致（总纲 §9）。**不得由组密钥派生**——轮换会让密钥变化，id 若绑定密钥则轮换即换组 |
| `target_id` | `group/<group_id>` | 沿用总纲 §6.0 的路径式命名空间（与 `article/<aid>` 同族），节点侧 `validTargetID` 直接可用 |
| `creator_id` | 创建者身份 id（公钥派生） | 名单事件的唯一签名权威（§4.2） |
| `epoch` | 整数，自 `1` 起单调递增 | 与组密钥一一对应；名单事件与消息事件均携带 |

### 3.2 组密钥与 epoch

- 组密钥：**32 字节随机**（AES-256-GCM 密钥），由创建者首建组时生成。
- 一个 `epoch` 对应一把组密钥。**加入与移出都不改密钥；只有移出才轮换**（§5.3）：加入者拿当前 epoch 密钥即可。
- 客户端本地保留历次 epoch 密钥以解历史消息（§5.1 的 `group_keys` 表）。
- **无前向安全**：旧 epoch 密钥长期留存于本地，KEK 泄漏即历史全可读（§7.1 风险 4）。

### 3.3 纯文本邀请码

**形态**：`base1:` + base64url(canonical JSON)，单行可复制粘贴。

```json
{
  "v": 1,
  "group_id": "<16 hex>",
  "target_id": "group/<16 hex>",
  "name": "<组名，可选>",
  "epoch": 1,
  "group_key": "<64 hex，32 字节>",
  "creator_id": "<身份 id>",
  "creator_pub": "<64 hex，Ed25519 公钥>",
  "created_at": 1759...,
  "sig": "<创建者身份私钥对上述字段的签名>"
}
```

- **签名域**：`canonical({v, group_id, target_id, name, epoch, group_key, creator_id, creator_pub, created_at})`（不含 `sig` 自身）。
- **入组校验**（客户端）：解码 → 用 `creator_pub` 验 `sig` → `creator_id == deriveIdentityId(creator_pub)` → 通过才落库。任一步失败即拒绝，错误信息统一为「邀请码无效或已损坏」，不区分原因。
- **自带 `creator_pub` 的理由**：入组方可能尚未联网，无法 `GET /v1/identity/{id}` 取公钥；自带公钥 + 自证 id 使邀请码**可离线自验**。
- 邀请码**含密钥**：拿到码即可入组。这是 ② 类「成员资格由客户端协商」的直接体现，**不是缺陷**；代价是码须经可信渠道传递、不该公开张贴（§7.1 风险 1）。

**续期码**（轮换后发放，§5.3）：同一格式、同一个 `group_id`，但 `epoch` 为**新值**、`group_key` 为新密钥、`created_at` 为新时间。入组方按 `epoch` 大小决定是否覆盖本地密钥（只接受更大的 epoch）。

### 3.4 `group.v1` 事件

统一走 `POST /v1/event`（签名头管准入 + `sig` 管归属），**与 `comment.v1` 完全同一段验签管线**。`body` 按 `action` 分两种：

**A. `action=msg`（发言）** —— 客户端原始 body（参与签名）：

```json
{
  "group_id": "<16 hex>",
  "action": "msg",
  "epoch": 3,
  "text_cipher": "<base64，密文 = sealWithNonce(当前 epoch 组密钥, nonce12, utf8(正文))>",
  "reply_to": "<16 hex，可选，指向同组某条 event_id>"
}
```

- 节点行为：验签 → 按 `BlobID(密文)` 落块 → 落事件行，`body_json` **减化**为 `canonical({group_id, action, epoch, payload_cid, reply_to})`（不含 `text_cipher`，正文只在块里存一份，与 `comment.v1` 同构）。
- **密文进签名域**：与 ① 类评论把正文放进签名域同理，保证「签了什么就存了什么」。节点从不解密。

**B. `action=roster`（名单）** —— 仅创建者发：

```json
{
  "group_id": "<16 hex>",
  "action": "roster",
  "epoch": 2,
  "member_ids": ["<id>", "<id>", "..."],
  "name": "<组名，可选>"
}
```

- 语义：**完整名单快照**（不是增量），且 `epoch` 必须严格大于节点当前记录的 epoch。
- 节点行为：验内容签名 → 校验 `actor == creator_id`（`epoch=1` 时首次登记即锁定）→ 校验 `epoch` 递增 → 更新名单投影（§4.2）。
- `roster` **不落块**（名单已在 `body_json`，节点侧本就可见，总纲 §3.1「节点只存成员名单（id 列表）」）。

**移出成员 = 一个带新 `epoch` 的 `roster` 事件 + 一把新组密钥**，两者通过**同一个续期码**送达剩余成员（§5.3）。

## 4. 节点侧改动（三件，其余零改动）

### 4.1 事件类型注册

`eventTypeRegistry` 增加 `"group.v1"`；`handleEventPost` 增加一个分支 `s.handleGroupEvent(...)`，按 `action` 再分流（`msg` → 落块 + 落事件行；`roster` → 名单投影）。

- body 校验用**严格键集**（多一个未知键即拒），与 `parseCommentBody` 同口径——防止「签了一份、存了另一份」。
- **仍不新开 blob 上传面**（缺口 G2）：② 类密文只能是 `group.v1` 的 `action=msg` 的一部分，天然受签名头准入 + 事件限速 + 内容签名三重约束。

### 4.2 名单表与 owner 锁（唯一新表）

```sql
groups(group_id TEXT PRIMARY KEY, creator_id TEXT NOT NULL, epoch INTEGER NOT NULL,
       member_ids_json TEXT NOT NULL, event_id TEXT NOT NULL, updated_at INTEGER NOT NULL)
```

- 首个 `roster` 事件（`epoch=1`）落一行，`creator_id = actor`（**锁定**）。
- 后续 `roster`：`actor` 必须等于已登记的 `creator_id`，否则拒绝（错误码 `group_owner_mismatch`）。
- `epoch` 必须严格大于当前值，否则拒绝（错误码 `group_epoch_stale`）——与 #27 提案的乐观锁同族口径。
- 名单是**完整快照覆盖**，不做增量合并。

**这张表是节点侧唯一的组状态**：它只含 id 列表与 epoch，**不含任何密钥、不解密任何内容**，与总纲 §3.1 的「节点只存成员名单（id 列表）」逐字一致。

### 4.3 匿名读接口（新增）

```
GET /v1/group/{group_id}?cursor=&limit=
```

与 `GET /v1/comment` 同构：匿名、`limit` 默认 30 / 上限 100、游标 `<created_at>_<event_id>`、满页才给 `next_cursor`。

```json
{
  "group": { "group_id": "...", "creator_id": "...", "epoch": 3, "member_ids": ["..."], "name": "..." },
  "events": [
    { "event_id": "...", "actor": "...", "created_at": 1759..., "payload_cid": "...", "epoch": 3, "action": "msg", "reply_to": null }
  ],
  "next_cursor": "1759..._<event_id>"
}
```

- `events` 只列 `action=msg`（名单不进会话流，已由 `group` 字段表达）。
- `group` 不存在（尚无任何 `roster`）时返回 404 `group_not_found`。
- 正文一律另取 `GET /v1/blob/{payload_cid}`（密文，节点不解释）。

**这条接口的代价必须写明**：索引匿名可读 ⇒ **「谁、何时、在哪个组发言」这一层元数据对外公开**。内容仍不可读（无组密钥）。之所以接受：① 总纲 §4 已定「② 类密文可匿名取字节」；② 若改走签名头 + 名单准入，节点就从「登记与缓存」变成「会拒服务的权威」，与总纲 §1 的节点定位相悖，且节点无法跨节点校验名单新鲜度。**不做成员准入**是本册的明确选择，不是遗漏。

### 4.4 零改动清单（逐条核对过）

| 组件 | 为什么不用改 |
|---|---|
| `internal/sync`（反熵、scrub、副本） | 比对的是 `blob_id`，② 类密文与 ① 类明文无差别（总纲 §7.4） |
| `POST /v1/event-sync` | 不按 type 过滤（缺口 G4），小组事件自动跨节点传播 |
| `GET /v1/blob/{id}` | 匿名取密文，语义未变 |
| 审核通道（`BASE_REVIEW_KEY`） | ② 类不可审（总纲 §12 第 9 条）；审核取正文按 `payload_cid` 取到的是密文，**不提供解密** |
| `internal/packexport` / `peersync` / 内容包规范 v1 | 小组消息不进包、不进 manifest，`schema_version` **不 bump** |
| 手机端 `comment_out` 队列表 | `wire` 列本已存整个请求体，小组发言原样复用（§5.4） |

## 5. 手机端设计

### 5.1 本地表

| 表 | 用途 | 与总纲 §8.1 的关系 |
|---|---|---|
| `groups(group_id, name, creator_id, epoch, member_ids_json, joined_at)` | 我参与的小组与当前名单 | **替换**原 `groups(group_id, member_ids_json, group_key_cipher)` 的单密钥形态 |
| `group_keys(group_id, epoch, key_cipher, created_at)`（新） | 历次 epoch 的组密钥，**密文列** `nonce:ct` | 新增：单行单密钥无法承载轮换 |

- `key_cipher` 由 `deviceKek()`（`kek_source='device'`）封装，复用 `sealWithNonce` / `openWithNonce`（#4 定案的应用层列级加密，**不新增 KEK 种类**）。
- 组消息**不进本地正文表**：读时从 `GET /v1/group/{id}` 拉索引 + `GET /v1/blob` 取密文 → 解密后仅在内存中渲染。本册**不做**消息本地持久化缓存（见 §8）。
- 禁用 `PRAGMA key` / `rekey` / `hexkey`（#4 红线，任何位置）。

### 5.2 新增模块

`apps/mobile/src/core/group.ts`：建组、邀请码编解码、入组、名单事件构造、轮换、发言编排、消息加解密。依赖方向与 `core/comment.ts` 一致——只依赖注入的 `StorageAdapter` / `LocalRepo` / 适配器，不 import `uni` / `plus`，因此可在 Node 下用 `core/fakes.ts` 完整测试。

### 5.3 移出与轮换（含「静默读不出」的处理）

轮换的三步，全部发生在创建者本地：

1. 生成**新组密钥**（32 字节随机），`epoch + 1`；
2. 发一个 `action=roster` 事件（新名单 + 新 epoch）；
3. 生成本组**续期码**（§3.3），经带外渠道发给**剩余成员**。

对剩余成员：粘入续期码 → `epoch` 更大即覆盖本地密钥 → 可解新消息。
对被移出成员：仍在旧 epoch，**新消息解密失败**。

**必须显式提示（硬要求）**：客户端在「索引里有我不知道的更大 `epoch`」或「解密失败」时，**不得静默跳过**，须在会话页原位提示原文：

> 小组密钥已更新，请向创建者索取新邀请码。

理由：这是纯粹的**静默失败**——不提示的话，用户只会看到「一片空白 / 消息消失」，无从判断是自己被移出、还是对方没发、还是网络问题。

**已知代价（用户在设计中确认接受）**：轮换的送达**强依赖创建者与每个剩余成员的带外可达性**；长期离线的成员不会自动换钥，其表现为上述提示而非自动修复。创建者离线则轮换停摆。本册不引入节点托管密钥包来消除这一代价（§8）。

### 5.4 离线发言：复用既有队列

- 断网发言 → 落的还是 `comment_out`（`text` 列存**密文**，列名语义为「正文载荷」，不承诺明文；`wire` 存 `type=group.v1` 的完整请求体）→ 联网由既有 `flushPending` 补发。
- **队列按 `wire` 原样重发**，节点按 `type` 分流，故补发逻辑零改动。
- 排队项在会话页待发区展示与删除，与评论页同一交互。
- 只在**网络不可达**时入队；节点返回任何 4xx / 5xx 一律原地报错不入队（沿用 #20 口径）。

### 5.5 UI

两个页面（加入既有 tab 结构，不改 #15 的四 tab）：

| 页面 | 内容 |
|---|---|
| 小组列表 | 已加入的小组（名称 / 成员数 / 当前 epoch）；「新建小组」→ 出邀请码可复制；「加入小组」→ 粘贴邀请码 |
| 小组会话 | 消息流（解密后渲染）、发言输入框、待发区、成员列表；顶部提供「生成续期码」（仅创建者）与「粘贴续期码」入口 |

## 6. 验收（AC）

| # | 场景 | 判定 |
|---|---|---|
| 1 | 建组与入组（离线） | A 建组出码 → B 断网粘码入组 → 双方本地 `group_keys` 第 1 条 epoch 一致、组密钥相同 |
| 2 | 邀请码防伪 | 篡改码中 `group_key` 任一字符 → 入组被拒，提示「邀请码无效或已损坏」 |
| 3 | 节点侧无明文 | 发言后直接读节点 `data/base.db` 与 `data/blobs/*` 原始字节，**不出现**消息明文 |
| 4 | 跨节点取件 | A 节点发言 → B 节点 `GET /v1/group/{id}` 列出该事件 → 取 `payload_cid` 密文块 → 用组密钥解密成功 |
| 5 | owner 锁 | 非创建者签名提交 `roster` → 拒绝，错误码 `group_owner_mismatch` |
| 6 | epoch 乐观锁 | 提交 `epoch` 不大于当前值的 `roster` → 拒绝，错误码 `group_epoch_stale` |
| 7 | 移出与轮换 | 创建者移出 B、发续期码给 C → C 粘码后可读新消息；B **解密失败并显示「小组密钥已更新」提示** |
| 8 | 离线发言 | 断网发言入队 → 联网自动补发**仅一条** |
| 9 | 匿名索引的边界 | 未入组者能列出索引与 `member_ids`，但取到的密文**无法解密** |
| 10 | 队列仅网络失败入队 | 节点返回 4xx → 不入队、原地报错；`comment_out` 行数不变 |

自动项（1–6、8–10）在 Node 下用 `fakes` + Go 单测跑通；真机项（7 的解密失败提示、UI 交互）待人工。

## 7. 风险与红线

### 7.1 残余风险（照实写，不粉饰）

1. **邀请码含密钥**：拿到码即可入组，且永不失效（无有效期、无一次性）。码须经可信渠道传递；创建者需知「码公开 = 组公开」。
2. **索引元数据公开**：谁、何时、在哪个组发言对外可见（§4.3 的明确代价）。
3. **无前向安全**：旧 epoch 密钥长期留在成员本地，被移出者仍可解**移出前**的全部消息；轮换只保护**之后**的新消息。
4. **KEK 泄漏 = 全部本地历史可读**：`group_keys` 是列级密文，同库存 KEK（#4 §5.1 已登记的固有边界）。
5. **同一组密钥下 GCM 随机 nonce 的碰撞界**（约 2^32 条消息）：单组消息量远低于此，登记留档；不做计数器 nonce（需跨设备协调状态，复杂度不值）。
6. **创建者丢钥 = 名单冻结**：无法增减成员，且无转让机制（§8）。组可继续发言（组密钥仍在成员本地），但名单事件再也发不出来。
7. **轮换送达依赖带外可达**（§5.3）：长期离线成员静默读不出新消息，只有提示，不会自动修复。
8. **成员名单对节点可见**：总纲 §3.1 的设计固有属性，不是本册引入的缺陷。
9. **② 类不可审**：小组内容节点无密钥，滥用治理只能靠客户端举报 + 成员自行移出（总纲 §12 第 9 条）。须在隐私政策写明。

### 7.2 红线

1. 节点侧**任何位置**不得出现解密组消息的代码路径；`payload_cid` 对应的块永不解密、不索引、不审核。
2. 组密钥与消息全文**不得**出现在日志、错误信息、上报字段中。
3. 全部密码学操作只经 `sealWithNonce` / `openWithNonce`；**不得**新写 AES 封装、不得引入新的密文格式。
4. 禁用 `PRAGMA key` / `PRAGMA rekey` / `PRAGMA hexkey`（#4 §5.2）。
5. 解密失败**必须**显式提示（§5.3），禁止静默跳过。

## 8. 明确不做

- 不做私信（#10）、不做小组内文件 / 图片 / 语音、不做消息撤回与编辑
- 不做群主转让、不做多管理员、不做双签名单
- 不做成员准入读控制（索引匿名可读，见 §4.3）
- 不做节点托管密钥包、不做二维码与扫码（只用纯文本邀请码）
- 不做消息本地持久化缓存（读时拉取、内存渲染，故离线**读不到**历史消息）
- 不做前向安全、不做密钥托管、不做成员治理（与 #23 名册无关）
- 不做跨设备密钥同步（多设备 = 导入同一身份备份，属既有能力）
- 不新增 HTTP 接口以外的接口面；不改内容包规范 v1、不 bump `schema_version`、不加配置项、不新增 KEK 种类
- 不做 iOS（总纲 §12 第 7 条）

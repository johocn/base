## 1. 范围与不做什么

**做三件事：**

1. 新增签名写路径 `POST /v1/submit`：已登记身份的作者把自己写的 `article` / `quiz` 直投本节点，验签通过即生效。
2. 定义**改写必重签**：不是接口层的君子协定，而是签名绑定 `content_hash` 的必然结果——作者改了正文就必须用新 `content_hash` 重签。
3. 定义**占用与授权**：`item_id` 一旦被占（无论有无归属），后来者一律拒绝；他人条目的改写与下架本册不做，留给第 3 册。

**明确不做：**

- **不做视频投稿**：视频与块上传（分块、断点续传、未引用块治理）归后续册；视频仍走 `import-video`。
- **不做块上传**：本册只收文本，正文随请求内联，不新增公开块写面。
- **不做课程/课时编排**（**2026-09-30 §0.3 收窄**）：只接受 `course/<cid>` 与 `course/<cid>/lesson/<lid>` 两个**容器形态**，其余 `course/...` 前缀（载体形态）仍拒；把内容组织进课程是运营动作，仍归导入器。
- **不做他人条目的改写与下架**：本册只把「拒绝」口径定死（§3.1）；改写与下架的授权模型归第 3 册。
- **不做审核队列**：作者本人投稿直发即生效，不引入 `pending` 状态；也正是因此名册仍保持「纯派生」（#23 §4.1 铁律）。
- **不做创作 UI**：节点页与手机端的投稿入口、编辑器归第 4 册。
- **不做成员治理**：不拉黑、不封禁、不处理举报、无申诉通道。
- **不在本册引入任何跨节点互动数据**（点赞 / 浏览 / 评论热度一律不进度量，沿用 #23 §4.1）。

## 2. 契约边界

### 2.1 `POST /v1/submit`（本册唯一的契约变更）

走既有 `requireAuth`（签名头 + 时间窗 + nonce），与评论写路径、`POST /v1/profile` 同一条鉴权路。按 `type` 判别载荷，风格与 `POST /v1/event` 的 `type` 分流一致。

请求体（`article`）：

```json
{
  "type": "article",
  "item_id": "article/<aid>",
  "title": "文章标题",
  "body_md": "Markdown 正文",
  "author_sig": "<hex>"
}
```

请求体（`quiz`）：

```json
{
  "type": "quiz",
  "item_id": "quiz/<qid>",
  "title": "题组标题",
  "question_json": "{\"schema_version\":1,\"questions\":[…] }",
  "author_sig": "<hex>"
}
```

`200 OK`：

```json
{ "item_id": "article/<aid>", "type": "article", "content_hash": "<hex>", "author_id": "<32 位 hex>", "created": true }
```

`created` 为 `false` 表示这是同一作者对已有条目的更新。

**硬约束：**

- `author_id` **只能**取自鉴权中间件解析出的身份。请求体**不得**携带 `author_id`——否则等于替他人署名。违反 → `400 author_id_forbidden`（与 #23 §5.2 的 `profile_id_forbidden` 同一口径）。
- `type` 取 `article` / `quiz` / `tag` 三者之一（`tag` 为 §0.2 补入）；其余值 → `400 item_type_unsupported`。
- `type` 必须与 `item_id` 前缀一致（`article/*` ↔ `article`，`quiz/*` ↔ `quiz`，`tag/*` ↔ `tag`）；不一致 → `400 item_type_mismatch`。
- `title` **必填**：去首尾空白后长度 1..200（rune），且不含控制字符（U+0000–U+001F、U+007F）。不通过 → `400 item_title_invalid`。
- 请求体**无需携带** `content_hash`；若携带则**一律忽略**，服务端只认自己按 §2.2 算出的值（携带一个错的反而会导致验签失败，即错值无法用来绕过验签）。

### 2.2 `content_hash` 口径（服务端算，客户端不传）

与 `internal/importer` 的既有口径**逐字节同构**，不新造规则：

| 载体 | `content_hash` |
|---|---|
| `article` | `hex(sha256(body_md 的 UTF-8 字节))` |
| `quiz` | `hex(sha256(question_json 的 UTF-8 字节))` |
| `tag`（§0.2 补） | `hex(sha256(按 seq 升序拼接的 "<kind>\t<target_id>\n" 的 UTF-8 字节))` —— 直接沿用 #14 §3.3 的**容器条目口径**，`kind` 取该目标的类型（`course` / `lesson` / `article` / `comment`） |

两条推论：

1. **quiz 的请求体给的是字符串而不是数组**。若给数组、由服务端重建 JSON，则「客户端所签的字节」与「节点所存的字节」要跨越 Go `json.Marshal`（HTML 转义 `\u003c`、字段序）与 TS `JSON.stringify` 的差异，签名必然抖动。给字符串则两端面对的是同一段字节，零解释空间。
2. **作者签名前必须先拿到 `content_hash` 的输入字节**，而它完全由作者自己要提交的字符串决定——所以客户端可以离线算出，无需先向节点要一次 hash（不做两阶段提交）。

### 2.3 `author_sig` 的待签字节（沿用 #23 §2.1，不改）

```
canonical_json({
  "alg":          "ed25519",
  "domain":       "base/author-v1",
  "item_id":      "<item_id>",
  "content_hash": "<按 §2.2 算出的 hex>",
  "author_id":    "<调用者 id>"
})
```

- 双端实现与契约向量均已在 #24 落地（`internal/protocol` 的 `AuthorSignBytes` / `packages/protocol-ts` 的对应实现 / `vectors/v1/authorsig.json`）。**本册不新增向量**——签名域一个字节都没动。
- 服务端验签用**本节点 `identities` 表**里该 `author_id` 的公钥（作者必先登记身份才能通过 `requireAuth`）。验不过 → `400 author_sig_invalid`，**不写入**。

### 2.4 `item_id` 形态与 `source` 取值

| `item_id` 形态 | 是否本册接受 | `items.source` | `items.type` |
|---|---|---|---|
| `article/<aid>` | 接受 | `article` | `article` |
| `quiz/<qid>` | 接受 | `quiz` | `quiz` |
| `tag/<名称>/<章>/<节>`（§0.2 补） | 接受 | `tag` | `tag` |
| `category/<slug>` | **拒绝**（只由导入器产出，见 #36 册子） | — | — |
| `course/...` 任意层级 | **拒绝** | — | — |

- `slug` 规则：`[a-z0-9][a-z0-9-]{0,63}`（小写字母 / 数字 / 连字符，首字符非连字符，总长 ≤ 64）。不合法 → `400 item_id_invalid`。
- **`tag` 的三段不适用 `slug` 规则**（标签名是人工词条，不是机器 slug）：三段各自 NFC 归一化 + 去首尾空白后必须非空且 ≤ 64 rune，其中 `/`、`\`、`%` 与控制字符做百分号编码；编码规则与其余边界见 #37 册子，本册只登记「三段编码后拼成 `item_id`」。
- 独立题库的 `items.source` 取 `quiz`（总纲 §6.0 的既有枚举，**不新增值**）；课程内题库沿用 #14 §2.1 的 `lesson`，本册不触碰。
- 本册只表达「不属于任何课程」的独立条目，**层级前缀仍归 #14**。

### 2.5 不可改

- `author_sig` 的待签字节定义（§2.3 引用的 #23 §2.1）——这是本册最硬的一处「不可改」。
- `blob_id` 算法与其输入（总纲 §3.2 铁律）；本册不产生块。
- `manifest.entries[]` 的结构、`pack.sqlite` 的 DDL 与列顺序。
- `dist_class` 之外的任何可见性维度。
- `items.source` / `items.type` 的既有枚举集合（本册只用既有值）。

## 3. 授权与占用

### 3.1 同 `item_id` 的三种现状

| 现状 | 行为 | 响应 |
|---|---|---|
| `item_id` 不存在 | 新建，`state='active'` | `200`，`created=true` |
| 存在且 `items.author_id` == 调用者 | **更新**：覆盖 `title` / 正文 / `content_hash` / `author_sig` | `200`，`created=false` |
| 存在且 `items.author_id` != 调用者，**或该条为空归属**（导入器存量内容） | **拒绝**，不写入、不覆盖 | `403 item_id_taken` |

- **空归属的存量条目也一律拒绝**：这是本册最重要的一条边界。否则任何人可以对存量 `article/<aid>` 投稿并「认领」它，把运营迁移进来的内容变成自己的贡献（直接污染名册）。空归属的正确收口方式是导入器按 front-matter 补齐归属，而不是投稿接口。
- 判定只看 `items` 表的 `author_id`，与 `state` 无关：已下架/墓碑条目同样算「被占」，**不允许靠重新投稿复活**（复活属第 3 册的治理动作）。

### 3.2 「改写必重签」为什么是机制而不是约定

`author_sig` 绑定的是 `content_hash`（§2.3）。而 `content_hash` 只由正文/题库字节决定（§2.2）。于是：

- 作者改了正文却沿用旧签名 → 服务端按**新字节**算出新 `content_hash` → 用旧签名去验必然失败 → `400 author_sig_invalid`，写入不发生。
- 作者改了正文并重签 → 验签通过，`content_hash` 与 `author_sig` 一起被替换。

也就是说，本册**不需要任何额外字段或状态**来表达「内容与签名是否同步」——不同步在数学上就无法通过验签。这是 #23 §8.7「改写必重签」的落地方式。

### 3.3 为什么不做他人改写（本册边界）

「谁能改写/下架别人的条目」正是第 3 册的主题（提案 → ≥2 人授权 → 生效）。本册若顺手放一个「治理者可覆盖」的口子，会出现两套并行的授权模型，且第 3 册的审批流程会被绕过。故本册只定义**拒绝**，不定义**放行**。

## 4. 数据落点与复用

- **零新表、零新列**：`items.author_id` / `items.author_sig` 已由 #24 落地；`profiles` 与名册不涉及本册。
- **写入口径沿用既有 store 层**（`articles` / `quizzes` 两张表、`source_rev` 取 `content_hash[:16]`、`state='active'`、`dist_class='public'`），本册不新增字段；唯一需要参数化的是 `items.source`（§2.4 的两行取值，既有 `UpsertQuiz` 固定写 `lesson`）。
- **导出侧无需改动**：`packexport` 已按本地 `identities` 回填 `entries[].author_id` / `author_sig` 并重建 `manifest.contributors`（#24 已落地）。因此本册投稿的内容**自动获得可跨节点验证的归属**。
- **不落 events、不跨节点同步**：投稿是「本节点内容库」的写入，传播仍靠既有导出与反熵。

## 5. 降级与错误处理

所有错误按契约 §3.3 的形状返回 `{"error": "<人读消息>", "code": "<机器码>"}`。任何人读文案都不构成契约，客户端只依赖 `code`。

**本册新增：**

| code | HTTP | 触发 |
|---|---|---|
| `item_id_invalid` | 400 | `item_id` 不符合 §2.4 的形态或 `slug` 规则，或带 `course/` 前缀 |
| `item_type_unsupported` | 400 | `type` 不是 `article` / `quiz` / `tag` |
| `item_type_mismatch` | 400 | `type` 与 `item_id` 前缀不一致 |
| `tag_not_governor`（§0.2 新增） | 403 | `type = "tag"` 且 `author_id` 不在本节点名册内（#23 名册 ∪ #33 治者集合） |
| `item_title_invalid` | 400 | `title` 去首尾空白后为空、超过 200 rune，或含控制字符（U+0000–U+001F、U+007F） |
| `item_body_too_large` | 413 | `body_md` 或 `question_json` 的 UTF-8 字节超过 `maxSubmitBytes`（文档级常量，32768） |
| `item_question_invalid` | 400 | `question_json` 不是合法 JSON、`schema_version` 非 1，或 `questions` 缺失/为空/不是数组 |
| `author_id_forbidden` | 400 | 请求体携带 `author_id` |
| `author_sig_invalid` | 400 | `author_sig` 不是 hex，或按 §2.3 验签不通过 |
| `item_id_taken` | 403 | 同 `item_id` 已存在且不属于调用者（含空归属存量条目） |
| `item_rate_limited` | 429 | 超过写限速 |

**沿用既有（不重复定义）：** `auth_missing_header`(400)、`identity_id_invalid`(400)、`auth_ts_out_of_window`(401)、`auth_nonce_replay`(401)、`auth_bad_signature`(401)、`identity_unregistered`(403)、`auth_body_too_large`(413)、`auth_body_read_failed`(400)。

**降级铁律：**

1. 任何失败都**不写入、不覆盖**：不存在「半条」结果。
2. 一处的失败**不影响其它条目**：投稿接口只处理单条，无批量语义。
3. `author_sig` 验不过时**不写 `items.author_id` / `author_sig`**，该条按 #23 §3.1 的口径就是「无归属」，也即不计贡献。

**限速（文档级常量，不做配置项）：** 按已验签身份 `submitPerMinutePerID = 6` / `submitBurstPerID = 3`；按客户端 IP `submitPerMinutePerIP = 30` / `submitBurstPerIP = 10`。复用既有 `ipLimiter`，维度口径与评论写路径一致。校准方式沿用 #23：改册子 + 改常量。

**内容大小：** `maxSubmitBytes = 32768`。它远小于 `authmw` 的请求体上限（64 KiB），故常规情况由本册的 413 先命中；两者都超时以 `authmw` 的 `auth_body_too_large` 为准。

**内容下限：** 本册**不设**任何内容下限。文章的 200 rune、题库的 3 题都只是 #23 §4.3 的**名册门槛**，不是入库门槛：1 个字的文章、1 道题的题库都可以入库、可以分发，只是不计贡献。这与「门槛是文档级常量、只影响名册」的既有口径一致。本册只设上限（`maxSubmitBytes`）。

## 6. 测试与验收

### 6.1 契约向量

**不新增向量。** 签名域未变，直接复用 #24 的 `vectors/v1/authorsig.json`（Go 与 TS 双侧消费已存在）。本册若有人提议新增向量，说明签名域被改了——那是改契约，不是本册范围。

### 6.2 Go 单测（节点侧）

覆盖：签名域复算（同一 `item_id` + `content_hash` + `author_id` 必得同一待签字节）；`content_hash` 与导入器口径同构（同字节同哈希）；`item_id` / `slug` / `type` 前缀校验的全部分支；`title` 校验边界（0 / 1 / 200 / 201 rune、控制字符）；`author_sig` 失配；三态占用（新建 / 同作者更新 / 他人拒绝 / 空归属拒绝）；限速触发。

- 端到端一条：投稿 → `GET /v1/contributors` 名册出现该 id → 导出包 → 解包节点复验归属通过。

## 7. 风险与留给后续册的开放项

### 7.1 `title` 不在签名域（本册最需要被看清的一处缺口）

**事实。** `author_sig` 的待签字节只有五个键：`alg` / `domain` / `item_id` / `content_hash` / `author_id`（§2.3，源自 #23 §2.1）。而 `content_hash` 对 `article` **只覆盖 `body_md`**、对 `quiz` **只覆盖 `question_json`**（§2.2）。因此 `title` 完全在签名之外；同理 `digest`、`published_at`、`tags_json`、`dist_class` 也都不在。

**后果。**

1. **接口之外的一切写路径都不受保护**：任何能写 `items.title` 的路径——运维直接在 SQLite 上改、重跑导入器、将来的管理面——改完标题后 `author_id` / `author_sig` 原封不动，**该条目的归属依然验签通过**。
2. **跨节点无从发现**：`title` 不参与任何签名或哈希，包级签名只证明「这个包是该节点发出的」（#23 §2.1(c)）。B 节点从 A 节点拿到「同一作者、同一正文、标题不同」的条目，**无法判定哪个标题是作者写的**。
3. **署名与呈现会自相矛盾**：读者看到的是「作者署名 + 一个作者没写过的标题」，而系统仍把它算作该作者的贡献。

**影响面界定（不做夸大的部分）。**

- 只影响**展示层字段**：名册计数只看 `author_id` 与质量门槛（article 门槛读 `body_md`），本缺口**不改变**计数结果。
- **不影响** `blob_id` 寻址、内容包完整性、块级去重与分发：这些由 `content_hash` 与包级签名覆盖的部分仍然成立。
- 不改写正文的攻击者拿不到任何**新内容**上的收益，价值主要在「误导标题 / 栽赃标题」。

**为什么本册不修。** 签名域定义被 #23 §2 与 §9 双重明示为「**契约出口，下游不得改**」。扩域会同时作废：已发布的 `authorsig` 向量、已签发的存量包与 `author_sig` 缓存列。#23 §9 也写明「若将来要求 title 也被签，需先改 #23 的签名域定义」——那是一次**重大改版**（走 #23 的 `## 0. 改版说明`），不是本册能顺手做的事。

**本册在接口层真正兜住的部分。**

- §3.1 的占用口径保证：**通过本册接口**不存在「他人改 `title` 而保留归属」的路径——只有 `author_id == 调用者` 才能写该 `item_id`。
- 空归属存量条目**一律拒绝占用**，堵死「先认领别人的 `item_id`、再改标题」这条最省事的栽赃路。
- 于是本缺口在**接口面上是闭合的**，残留的是「绕开接口的本地写」——那属于节点运维的信任域（与 #23 把 `items.author_id` 定位为「本地缓存，非权威」是同一层级的让步）。

**遗留缺口（本册不修，明确登记）。**

1. 本地直写（运维 SQL / 重跑导入器 / 将来的管理面）可改 `title` 而归属不动，且不产生任何可检测痕迹。
2. 中继节点再导出时若其本地 `title` 与真源不同，接收节点同样无从发现（与 #23 §8 的「中继节点再导出归属降级」是两个独立的缺口，不要混为一谈）。
3. 若第 4 册的创作 UI 允许作者改标题，该修改**同样不走签名**——届时要么接受「标题变更不重签」，要么先改 #23 的签名域。

**若要收口。** 唯一正解是把 `title`（乃至 `digest` / `tags`）纳入 `author_sig` 的待签字节，即改 #23 §2.1 的契约出口并重出向量与重签存量。这是 #23 改版或第 3/4 册的事，本册只做标注，不擅自扩域。

### 7.2 无下架能力

本册只写不撤：作者投错了既不能删也不能下架（§1）。**后果**：错误内容会一直计贡献，直到第 3 册给出治理动作。这是刻意的取舍——「谁能下架」正是第 3 册的主题，在本册顺手开一个「作者可撤自己的」口子，会把墓碑语义与第 3 册的审批边界搅在一起。

### 7.3 无法在线投进课程

本册拒绝 `course/...` 前缀（§2.4），因此投稿内容一律落在「未归类」区。**后果**：把内容组织进课程仍需运营侧用导入器操作。这是刻意的边界（课程编排是组织行为，不是投稿行为），但意味着第 4 册的创作 UI 若想「投稿时直接选课程」，必须先回到本册或 #14 改契约。

### 7.4 灌水仍未根治

沿用 #23 §8 的风险 3：门槛只挡「空文章」，挡不住「200 字废话 × 100 篇」。本册新增的限速只约束**速率**，不约束**质量**。真正的抗刷需要质量信号，而质量信号几乎必然跨节点——与 #23 §4.1 的铁律冲突。若将来必须引入，**需先改总纲**。

### 7.5 冷启动死锁延续

本册让「有作者」变得更容易（投稿不再依赖会跑命令行的运营），但没有改变 #23 §8 的冷启动死锁：只有 1 名投稿人时，第 3 册的「≥2 人授权」仍不成立。本册不解决，只把路铺平——第一个投稿人不需要任何审批就能投。

### 7.6 身份即贡献的固有代价

客户端自持密钥；换设备若未用密码托管取回私钥，作者无法再更新自己的条目（`author_id` 变了 → 全部 `item_id` 判为 `item_id_taken`）。这与 #23 §8 的风险 4 同源，本册不修，但把后果放大了一层：不只是「贡献归零」，而是「原有条目**再也不能被本人更新**」。

## 0. 改版说明

### 0.1 2026-09-29 初版（spike 定案）

**动机（本册子存在的唯一理由）**：总纲 §8.2 要求「让 `plus.sqlite` 本地库文件在设备上以密文落盘，且**用户可自由开关**」，并写死「开工前必做 spike」：uni-app 的 `plus.sqlite` 是否提供加密参数（如 SQLCipher 支持），且**不预设结论**。本册子即该 spike 的定案。它阻塞 #9（学习小组）与 #10（私信）——两者都要往本地库写②类密文，落盘形态不定就无法开工；#11（L4a 部署文档）也等这层结论。

**结论先行**：

- **`plus.sqlite` 不支持库级加密。** 官方 API 面没有任何加密入口（§3 E1）。
- **SQLCipher 在 uni-app 里只能靠 UTS 原生插件**：Android-only、需自定义基座、**iOS 不支持**（§3 E2）。这与 #3 的 TLS spike 否决 F2 的理由**逐字同构**——「超出『纯 uni-app、无原生代码』的既定预算，且 iOS 需另做一份」（§3 E3）。
- 故总纲 §8.2 的「**整库密文 + 可自由开关**」在既定预算内**不可达**，整体搁置；退路定案为**应用层列级加密**（§4）。
- **代码零改动**：现行 `deviceKek()` 已是该退路的基线形态，只是它的定位从「临时形态」变为「定案形态」。

**作废内容（已同步回填总纲 §0.3）：**

- §8.2 的目标句「本地库文件整体密文落盘 + 用户可自由开关」作废。
- §12.1 的 L3 行「可开关；实现待 spike，含退路」作废。
- §12 第 11 条「本地库加密密钥派生自本机私钥」作废——该表述本身是**死锁**（§4.2）。

**保留并沿用：** 私钥永不落明文（`identity.privkey_cipher`）、`saveLocalIdentity` / `loadLocalIdentity` 的调用契约与「只替换 `deviceKek()` 一个实现」的重构点、`KekSource` 三值枚举、① 类公开内容不做本地加密、私钥导出/备份与重装降级路径的要求。

## 2. spike 问题（原文）

总纲 §8.2 逐字：

> **待验证项（开工前必做 spike）**：uni-app 的 `plus.sqlite` 是否提供加密参数（如 SQLCipher 支持）。**本设计不预设结论。**
>
> 若不支持，退路优先级：
> 1. 敏感表（`identity` / `groups` / `messages`）单独加密列，其余表保持明文；
> 2. 仅加密私钥与组密钥，私信正文在本地以密文存储、读时解密。

## 3. 证据

**取证方式说明（重要）**：本次为**文档面核实**，非真机实测——本机无可用的 Android / iOS 设备。之所以文档面足够，理由同 #3 的 TLS spike（`plans/2026-09-26-base-identity-tls-plan.md` Task 1）：

1. 本问是**存在性问题**（「API 面上有没有这个参数」），一手文档即终局证据，不需要设备复现；
2. 若参数存在，官方文档不可能只列 4 个；
3. 退路的比较**不依赖实测结果**——三条路里两条要原生代码，答案与设备无关。

### E1：`plus.sqlite` 的 API 面没有加密入口

一手来源：DCloud 官方 HTML5+ 规范 `https://www.html5plus.org/doc/zh_cn/sqlite.html`。

- 模块共 **6 个方法**：`openDatabase` / `isOpenDatabase` / `closeDatabase` / `transaction` / `executeSql` / `selectSql`。
- `openDatabase(options)` 的参数**只有 4 个**：`name`（String，必选，数据库名称）、`path`（String，必选，数据库路径）、`success`（可选）、`fail`（可选）。
- 全模块**无** `key` / `password` / `cipher` / `encrypt` 类参数；官方示例亦无。

→ **结论：`plus.sqlite` 不能打开或创建加密数据库。**

### E2：SQLCipher 在 uni-app 生态只有 UTS 原生插件形态

一手来源：DCloud 插件市场 `https://ext.dcloud.net.cn/plugin?id=28979`（「SQLCipher 加密数据库操作插件」）。

- 定位：「面向 uni-app **App-Android** 的 **UTS 原生插件**」；引擎 `net.zetetic:sqlcipher-android:4.17.0`。
- 安装与构建原文：「需要使用**自定义基座**或正式原生构建，**普通 H5、微信小程序和 iOS 不支持**」。
- 平台兼容表仅 Android 列为可用。

→ 走这条就是引入原生代码，且 **iOS 整条路径缺失**（总纲 §12 第 7 条「二期前不做 iOS」可缓解但不能替代）。

### E3：与 #3 的 F2 否决理由同构（既定预算先例）

`plans/2026-09-26-base-identity-tls-plan.md`：

> **F2**：用 Android 原生插件做 pinning。**超出"纯 uni-app、无原生代码"的既定预算**，且 iOS 需另做一份。

「纯 uni-app、无原生代码」是 #3 已经确立并据以定案的**既定预算**，不是本册子新引入的限制。整库密文的处境与 F2 逐字同构，故同样否决。

## 4. 退路定案

### 4.1 落点：应用层列级加密（总纲退路 ① 与 ② 是同一种技术）

**判断：总纲退路 ①（敏感表单独加密列）与 ②（仅加密私钥与组密钥）在实现上是同一件事**——`plus.sqlite` 既然没有引擎级能力，能做的只有应用层；① 与 ② 的差别仅在**覆盖面**，不在**技术**。故本册子不再维持两档并列，统一表述为：

> **应用层列级加密：敏感字段在写入前于客户端加密，读时解密。覆盖面按表需要决定，不做「表级 / 库级」区分。**

定案覆盖面（按总纲 §8.2 的落点收窄）：

| 对象 | 形态 | 现状 |
|---|---|---|
| 身份私钥 | 密文列 `identity.privkey_cipher`（`nonce:ct`） | **已落地**（S1） |
| 组密钥 | 密文列 | 待 #9 落地 |
| 私信正文（本地持久化） | 密文存储、读时解密 | 待 #10 落地 |
| ① 类公开内容（`items` / 块文件） | **保持明文** | 定案不改 |

**为什么 ① 类坚决不加密**：① 类是可匿名公开分发的公开内容，本地加密**隐私收益为零**，却把「重装后重新从节点下载 ① 类内容」从可选降级路径变成**唯一路径**，并给每次读取加一次解密成本。这与总纲 §12.1「① 类公开内容做 E2E 加密」被列为明确不做是同一条理由。

### 4.2 KEK 来源：维持 `device`，并把「派生死锁」留档

定案：`kek_source = 'device'`——随机 32 字节存应用私有存储（键 `identity.device_kek`）。**本册不引入用户口令，不引入设备安全存储。**

**必须留档的矛盾**：总纲 §8.2 原文写「密钥来源：**由本机私钥派生**，不新增独立口令」。这一条**在逻辑上不可实现**——私钥自己就存在 `identity.privkey_cipher` 里、由 KEK 加密；若 KEK 再由私钥派生，则**没有任何东西能先解出私钥**，鸡生蛋死锁。这解释了为什么 S1 期实际落的是 `device`（总纲 §8.2 的 2026-09-26 回填注已承认）。

三条可能的出路，逐条否决并留档，以免将来反复讨论：

| 出路 | 可行性 | 结论 |
|---|---|---|
| **由私钥派生** | 死锁，不可实现 | **作废**（总纲 §0.3 已回填） |
| **用户口令派生**（`kek_source='password'`） | 技术可行，是唯一能真正撬开死锁的纯 uni-app 路径 | **不采纳**：违背总纲「不新增独立口令」的既定约束，且新增「忘口令 = 私钥不可读」这一可避免的失联面。`KekSource` 保留该枚举值作为**将来升级路径**，不在本册实施 |
| **设备安全存储**（Android Keystore / iOS Keychain） | 安全性最优 | **否决**：需原生插件，同 E2 / E3 理由；`kek_source='device+password'` 同为保留值 |

→ 结论：**`KekSource` 三值枚举一个都不删**（删了会让将来的升级路径变成破坏性变更），只把其含义从「待收敛」改为「已定案，保留升级位」。

### 4.3 开关：随整库密文一并搁置，且不提供敏感字段的关闭开关

总纲要求「用户可自由开关」的**动机**是「担心加密影响性能 / 兼容性」。既然库级加密不做，这个开关就**失去了目标物**（没有「开 = 整库密文 / 关 = 整库明文」这个二态）。

同时**不为敏感字段加密提供关闭开关**：私钥密文落盘是安全底线，允许关掉等于允许用户把私钥写成明文，不该存在这个选项。现状即是如此（`deviceKek()` 无条件生效），**零改动**。

## 5. 残余风险与红线

### 5.1 残余风险（照实写，不粉饰）

1. **不抗 root / 越狱的本地读取**：KEK 与密文**同库**，能读到库文件就能读到 KEK 再解出私钥。本层只挡「应用沙箱外的普通读取」与「另一台设备上的拷贝」。
2. **`plus.sqlite` 库文件本身仍是明文**：`items`、块索引、评论事件等一律可读。② 类密文之所以安全，靠的是**内容在写入前已由客户端加密**（总纲 §9），不是靠本地库加密。
3. **「① 类重装后重新下载」仍是必须路径**：本来就被整库加密逼成必须，本册不改这一点，只是不再额外增加负担。
4. **KEK 丢失 = 私钥不可读**：KEK 无备份。但**这不是新增风险**——它由总纲 §12 第 10 条「必须提供私钥导出/备份」与 §8.2「重装降级路径」承担，**这两条要求继续有效**，归 #11 的部署/运维文档与后续身份册子。

### 5.2 红线：全面禁止 `PRAGMA key` 及其同族

**`plus.sqlite` 使用的是平台自带的普通 SQLite，不是 SQLCipher / SEE 构建。** `PRAGMA key` / `PRAGMA rekey` / `PRAGMA hexkey` 对它而言是**未识别 PRAGMA，会被静默忽略**——不报错、不返回失败、不产生任何加密效果。

因此：

> **红线：本项目任何位置（生产代码、测试、脚本、SQL 字符串、文档示例）一律不得出现 `PRAGMA key` / `PRAGMA rekey` / `PRAGMA hexkey`。** 误加会产出「看起来已加密、实际明文」的库，这是**比不加密更危险**的假安全感。

**建议的机械化护栏**（归本册之后的任一实施册子，本册不实施）：在 mobile 的门禁里加一条全仓 grep 断言，命中即失败。

## 6. 对下游的接口约束（#9 / #10 / #11）

- **#9（学习小组）/ #10（私信）**：本地②类密文一律走**应用层列级加密**——组密钥 / 私信正文在写入 `plus.sqlite` **之前**于客户端加密。**不得**假设本地库有任何引擎级保护，**不得**出现 §5.2 的 PRAGMA 同族。KEK 复用 `deviceKek()`（同一 `kek_source='device'`），**不新增 KEK 种类**；若 #9 需要独立组密钥，那是**内容密钥**而非 KEK，须与 KEK 分层写清。
- **#11（L4a 部署文档）**：节点侧磁盘静态加密与手机本地库是**两条独立结论**——L4a / L4a′ 照原样实施，本册不影响它，也不必等待本册。但 §5.1 第 4 条要求的两条用户侧退路（私钥导出/备份、重装后重新下载①类内容）需要 #11 一并在部署/运维文档中可可执行化。
- **通用**：本册**零新增 HTTP 接口、零数据库 schema 变更、零配置项**。`kek_source` 语义已定案，后续册子不得再把它当作「待收敛」而随意收缩。

## 7. 明确不做

- 不做整库密文（需原生插件，超出既定预算）
- 不引入 UTS / 原生插件，不引入自定义基座
- 不引入用户口令，不引入设备安全存储（Keystore / Keychain）
- 不做「敏感字段加密」的用户开关
- 不对 ① 类公开内容做本地加密
- 不实现任何业务功能（本册结论为代码零改动）
- 不做 iOS 平台能力评估（总纲 §12 第 7 条：二期前不做 iOS）

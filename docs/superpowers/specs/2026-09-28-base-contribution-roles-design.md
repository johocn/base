# base 贡献度量与动态角色设计（治理主线）

- 日期：2026-09-28
- 上游：总纲 `specs/2026-09-25-base-distributed-learning-design.md`（唯一上游，冲突时先改总纲）
- 范围：**本节点内容贡献的度量，与「贡献前 10 名自动成为内容治理者」的角色派生** —— 含作者归属的签名契约、度量口径与质量门槛、名册公开读接口、公开资料最小写路径
- 本册子**不覆盖**：投稿写入接口与内容更新授权（第 2 册）；审批工作流本体「提案 → ≥2 人授权 → 生效」（第 3 册）；手机端与节点页创作 UI（第 4 册）；成员治理（拉黑 / 封禁 / 申诉）；任何跨节点互动数据（点赞 / 浏览 / 评论热度）

## 0. 改版说明

### 0.1 2026-09-28 初版

**新增（本册子首次定义）：**

- 作者归属的**签名契约**：`manifest.entries[].author_id` / `author_sig` 与 `manifest.contributors`（§2.1）
- 名册度量口径：文章数 + 质量门槛，输入只吃本节点可独立验证的数据（§4.1、§4.2、§4.3）
- 角色的**实时派生**模型：不存名册、无任期、跌出即失权（§4.4）
- 公开读接口 `GET /v1/contributors`（§5.1）
- 公开资料最小写路径 `POST /v1/profile` 与本地 `profiles` 表（§3.2、§5.2）

**明确沿用、不改动：**

- 身份模型：客户端自持 Ed25519 私钥，`id = sha256(pubkey 原始 32 字节)[0:32]`；**节点不签发身份、不发放 JWT**（总纲 §0.2、§4）
- `blob_id = hex(sha256(逻辑字节))[0:32]` 与磁盘布局（总纲 §3.2）
- 可见性只有 `dist_class` 一维（总纲 §3）；本册**不引入任何新的权限维度**
- 内容包规范 v1 的既有字段名与类型；本册新增字段**全部可选**，旧包解析后降级为「无归属、不计贡献」，故**不 bump `schema_version`**、不重签历史包、不动存量内容哈希
- 写路径鉴权一律走既有 `internal/httpapi/authmw.go`（签名头 + 300s 时间窗 + nonce 防重放），**不新增鉴权形态**
- 节点间事件反熵口径（册子 #19）；本册的 `profiles` 与 `items.author_id` **不进 events、不跨节点同步**

## 1. 范围与不做什么

**做五件事：**

1. 定义作者归属的**签名契约**，使任意节点都能独立验证「这一条是谁写的」，不依赖对发行节点的信任。
2. `items` 表新增 `author_id` 列 + 索引，作为已签名事实的**本地缓存**，供快速计数。
3. 定义度量口径与质量门槛，**实时派生**本节点贡献前 10 名的治理者名册。
4. 新增公开读接口 `GET /v1/contributors`，匿名开放。
5. 新增本地 `profiles` 表与最小写接口 `POST /v1/profile`，让名册能显示昵称（展示层，作者主动设置）。

**明确不做：**

- **不做投稿写入接口**：本册只定归属契约与验签口径；投稿时如何签 `author_sig`、如何落 `items.author_id`、内容更新与改写他人条目的授权，全部归第 2 册。
- **不做审批工作流**：提案、投票、≥2 人授权、生效、防重复投票，一律归第 3 册。
- **不做创作 UI**：节点页与手机端的创作入口、编辑表单归第 4 册。
- **不做成员治理**：不拉黑、不封禁、不处理举报、无申诉通道。
- **不含任何跨节点互动数据**：点赞、浏览、评论热度一律不进度量（理由见 §4.1）。
- **不做名册与昵称的跨节点同步**：`profiles` 与名册均不跨节点；昵称是展示层，缺失即回退（§5.1）。
- **不做治理者操作日志与审计视图**。
- **不引入配置项**：门槛数值是文档级常量，不进节点配置文件。
- **不改 `tools/migrate`**：迁移进来的历史内容无归属身份，天然不计贡献。

## 2. 契约边界

### 2.1 作者归属的签名契约（本册唯一的契约变更）

现状：manifest 由**节点 issuer 私钥**签名（`internal/protocol/manifest.go`），只证明「该节点发出了这一包」，**不证明「谁写的」**。本册新增两层：

**(a) `manifest.entries[]` 新增两个可选字段**

| 字段 | 类型 | 含义 |
|---|---|---|
| `author_id` | string | 该条目的作者身份 id（32 位小写 hex）；空 = 无归属 |
| `author_sig` | string | 作者**本人**的 Ed25519 签名（hex）；空 = 无归属 |

`author_sig` 的签名字节定义为：

```
canonical_json({
  "alg":          "ed25519",
  "domain":       "base/author-v1",
  "item_id":      "<item_id>",
  "content_hash": "<条目 content_hash>",
  "author_id":    "<author_id>"
})
```

`canonical_json` 沿用既有实现——Go 侧 `internal/protocol` 的 Canonicalize、TS 侧 `packages/protocol-ts` 的对应实现，**不新增编码规则**。`domain` 字段用于域分隔，避免与其他签名场景交叉复用。

**(b) `manifest` 新增 `contributors` 映射**

```json
"contributors": { "<author_id>": "<pubkey_hex>" }
```

- 公钥**内嵌**，而非查接收节点本地的 `identities` 表——否则跨节点验证仍依赖「对方是否登记过」，归属的可验证性就退化成节点间的信任。
- **自证**：`IdentityID(pubkey) == author_id`，其中 `IdentityID` 沿用既有派生（`sha256(pubkey 原始 32 字节)` 的 hex 前 32 字符）。改公钥即失配，篡改无收益。

**(c) 两层签名的分工**

| 层 | 签名者 | 证明什么 |
|---|---|---|
| `manifest.signature` | 节点 issuer | 这一包由该节点发出、内容完整 |
| `entries[].author_sig` | 投稿身份 | 这一条确实由该作者署名 |

由此得到一条关键性质：**验证者不需要信任发行节点，即可确认归属**——拿 `contributors[author_id]` 的公钥验 `author_sig`，并复算 id 自证。

**(d) 导出与入库必须同口径**

三个新增字段必须**同时**出现在：`internal/protocol` 的结构定义、导出侧 `internal/packexport` 白名单、入库侧 `ImportPack` 解包。任一处漏掉，归属就会在包层静默丢失——这与册子 #14 给 `segments` 补 `packexport` 白名单是同一类坑。

**再导出时 `contributors` 怎么重建**：节点本地只缓存了 `author_id` / `author_sig`，没缓存公钥。重建走本地 `identities` 表按 `author_id` 反查（投稿必然登记过该身份），**零新表**；查不到公钥的条目不导出 author 字段，降级为无归属，不影响其余条目。

### 2.2 不 bump `schema_version`

新增字段全部可选（`omitempty`）。旧包缺失这些字段时解析为空串，语义即「无归属、不计贡献」——这是**正确的降级，不是错误**。因此不改 `schema_version`、不重签历史包、不动存量内容哈希。

### 2.3 不可改

- `blob_id` 的算法与输入不变（总纲 §3.2 铁律）。本册动的是**条目级**字段与 manifest 结构，**块级寻址不动**。
- `entries[].source` / `type` 的既有取值集合不变，**不新增枚举值**；三种载体沿用 `article` / `video` / `quiz`。
- 可见性仍只有 `dist_class`。**本册不把「贡献」变成一种可见性**。

## 3. 数据模型

### 3.1 `items` 新增两列（本地缓存，非权威）

```
ALTER TABLE items ADD COLUMN author_id  TEXT NOT NULL DEFAULT ''
ALTER TABLE items ADD COLUMN author_sig TEXT NOT NULL DEFAULT ''
CREATE INDEX IF NOT EXISTS idx_items_author ON items(author_id, state)
```

- **不是权威**：权威在签名里（§2.1）。这两列是「入库时已验签通过」的本地缓存，避免每次算名册都重新验签全部条目。
- `author_sig` 必须一并留存（原始签名 hex），否则事后无从重验，AC 3/4 也无法独立复现。
- **验签只在入库时执行一次**：第 2 册投稿落库、以及 `ImportPack` 解包（`internal/store` 导入路径）时，节点用该包 `contributors[author_id]` 的公钥验 `author_sig`；通过才写这两列，失败则**两列都保持空**（该条目等于无归属）。
- **运行期名册计算只读缓存列，不重验**（成本考虑）。因此 §6「以签名为准」的含义是**入库时以签名为准**，不是每轮重算都验。
- **加列迁移必须显式做**：`internal/store/schema.go` 的 `schemaStatements` 全是 `CREATE TABLE/INDEX IF NOT EXISTS`，**对既有表不补列**。新增这两列必须仿 `eventColumnMigrations` 做「列存在性检查 + 逐条 ALTER」，否则老库上 `SELECT author_id` 直接报错。
- 存量导入内容（`import-md` / `import-video` / `tools/migrate`）两列均为空。

### 3.2 `profiles`（本地表，展示层）

```
CREATE TABLE IF NOT EXISTS profiles(
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  updated_at INTEGER NOT NULL
)
```

- 一行 = 某身份**主动设置**的公开昵称。
- 与 `escrow` **完全无关**：`escrow.username` 是为「换设备取回私钥」而设的，本册**不复用它、不因本册而公开**。
- 不跨节点同步、不进 events、不参与反熵。
- **不要求 `name` 唯一**（主键是 `id`），避免昵称抢注。

### 3.3 为什么不需要新增权威存储

名册是**派生值**，不是状态。它完全由「已签名内容」决定，因此不需要表、不需要结算、不存在「生效时间」、不需要同步。这是本册最省的一处设计，也是「持有相同内容的两个节点必得相同名册」这一性质的来源。

## 4. 名册规则

### 4.1 输入只含本节点可独立验证的数据（铁律）

名册是**授权依据**。凡掺入跨节点数据（点赞、浏览、评论热度），各节点算出的前 10 名就会不同——同一身份在 A 节点是治理者、在 B 节点不是，「≥2 人授权」随即失去可判定性，整个自治就散了。

因此：**度量输入只能是「本节点持有、带作者签名、可独立验签」的内容条目。**

### 4.2 计入条件

一条内容计入其作者贡献，当且仅当**全部满足**：

1. `state = 'active'`（被下架或已墓碑的条目不计）；且
2. `items.author_id` 非空——该值本身即「入库时 `author_sig` 已验签通过」的凭证（§3.1）；且
3. 达到该载体的质量门槛（§4.3）。

名册计算**只读缓存列，不重验签名**；验签发生在入库那一次（§3.1）。

### 4.3 质量门槛（文档级常量）

| 载体 | 门槛 |
|---|---|
| article | `body_md` 去除全部空白后，字符数（rune）≥ 200 |
| video | `media_meta.duration` ≥ 60 秒 |
| quiz | `question_json` 中的题目条数 ≥ 3 |

- 数值写死在代码常量里，**不做配置项**；校准走「改册子 + 改常量」。
- 三种载体**各计 1 条**；**同一 `item_id` 无论被重写多少次，都只计 1 条**。
- **时长为 0（未知）的视频不计贡献**：导入器的 `-duration` 默认 0 表示未知（`cmd/based/importvideo.go`）。导入视频必须带 `-duration`，否则该视频不计入作者贡献。

### 4.4 排序、截断与生效

| 项 | 规则 |
|---|---|
| 主序 | 条数**降序** |
| 次序 | 条数相同时按 `author_id` 字典序**升序**（纯确定性 tiebreak，保证各节点结果一致） |
| 截断 | 取前 **10** |
| 柔性名额 | 不足 10 人就有几名；**≥1 条即入选**；名册为空返回空数组，不报错 |
| 生效 | **实时派生**——不存名册、无任期；跌出前 10 **立即**失去治理者身份 |

### 4.5 与总纲铁律的兼容性

「前 10 名自动成为治理者」**不违反**总纲 §0.2 / §4 的「节点不签发身份、不发放 JWT」：

- 身份仍由客户端自持私钥派生，节点未参与。
- 角色**不是**节点颁发的凭证，而是**任何一方都能独立重算的公开函数**：`f(已签名内容集合) → 名册`。节点在此仍是「登记与派生」，不是「授权发号」。
- 因此客户端**不需要**向节点申请，也不需要节点返回「你是治理者」，自己算即可（§5.3）。

## 5. 接口

### 5.1 `GET /v1/contributors`（匿名开放）

与 `catalog` / `manifest` / `pack` 同级，**无需登录、无需签名头**。

```
200 OK
{
  "contributors": [
    { "id": "3f2a1c9b...", "count": 7, "name": "阿茶" },
    { "id": "b81c9e02...", "count": 7, "name": "b81c9e02" }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `id` | 身份 id（32 位小写 hex） |
| `count` | 计入贡献的条目数 |
| `name` | 取自本地 `profiles`；该身份未设置时**回退为其 `id` 前 8 位** |

- **固定返回前 10**，不加 `limit` / `since` 参数（契约最小）。
- `id` + `count` + 顺序是**授权依据**：只要两节点持有相同内容，这部分**必然一致**。
- `name` 是**展示层**：`profiles` 不跨节点，故同一名册在不同节点上昵称可能不同或缺失。**不影响任何判定**（§4.5）。
- 不返回条目清单、不返回投稿时间、不返回任何内容 id。

### 5.2 `POST /v1/profile`（签名写路径）

复用既有鉴权中间件 `internal/httpapi/authmw.go`（`X-Base-Id` / `X-Base-Alg` / `X-Base-Ts` / `X-Base-Nonce` / `X-Base-Sig`），与评论写路径**同一条路**。不新增鉴权形态，不新增事件类型。

```
请求体：{ "name": "阿茶" }

200 OK：{ "id": "<调用者 id>", "name": "阿茶" }
```

- **硬约束**：写入的 `id` **取自鉴权中间件解析出的调用者身份**，请求体**不得**携带 `id`——否则等于伪造他人昵称。
- `name` 校验：去首尾空白后（rune 计）长度 1..32；不允许含控制字符（U+0000–U+001F、U+007F）。不通过返回 `400` + `profile_name_invalid`。**入库的是去首尾空白后的值**（不是原文）。
- 幂等：同一 `id` 重复提交即覆盖（`ON CONFLICT(id) DO UPDATE`）。
- 只写本地 `profiles` 表，**不落 events、不跨节点传播**。

### 5.3 客户端如何判断「我是治理者」

无需任何鉴权调用：拉 `GET /v1/contributors`，比对当前身份 id 是否在返回列表中即可。治理者身份因此是**可独立推导的公开事实**，而不是需要联网申请的凭证。

（真正的权限判定发生在提案审批环节，归第 3 册；第 3 册按「投票时刻实时查询本节点名册」判资格。）

## 6. 降级与错误处理

任何一条不满足条件即**跳过该条目**，绝不中断整张名册的计算：

| 情形 | 处理 |
|---|---|
| **入库时** `author_sig` 缺失或验签失败 | 两列都写空（该条目等于无归属），记一条告警；**不阻断该包的其余条目** |
| **入库时** `contributors` 缺该 id，或 `IdentityID(pubkey) ≠ author_id` | 同上——改公钥即失配，篡改无收益 |
| **入库时** `author_id` 为空（存量导入内容） | 两列都写空 |
| **计算名册时** `author_id` 为空 | 跳过 |
| **计算名册时** `state ≠ 'active'`（含被下架、墓碑） | 跳过 |
| **计算名册时** 未达质量门槛（含 video `duration = 0`） | 跳过 |
| 名册为空（新节点） | 返回 `{"contributors":[]}` + `200`，不报错 |
| `profiles` 缺该身份 | `name` 回退 `id` 前 8 位，**不影响名册成立** |

## 7. 测试与验收

### 7.1 契约向量（Go 与 TS 双消费）

`vectors/v1/authorsig.json` 新增，沿用既有向量文件组织（固定私钥 + 固定输入 + 期望规范化字节 + 期望签名 + 期望派生 id）。**Go（`internal/protocol`）与 TS（`packages/protocol-ts`）两侧测试必须同时消费**——总纲 §5.3 对齐铁律。

`packages/protocol-ts` 需新增 `author_sig` 的验签实现，供手机端与节点页独立判定归属。

### 7.2 Go 单测

- **门槛边界**：article 199 / 200 字（含空白消歧）、video 59 / 60 秒、video `duration=0`、quiz 2 / 3 题。
- **排序**：条数降序 + 同条数按 `author_id` 升序，结果稳定可复现。
- **柔性名额**：只有 3 人时返回 3 条；0 人时返回空数组。
- **截断**：12 个身份投入不等数量 → 断言只返回 10 条、边界名次正确。
- **去重**：同一 `item_id` 重写 5 次 → 仍只计 1 条。
- **跳过路径**：空 `author_id` / 伪 `author_sig` / 公钥失配 / `state='removed'` / 未达门槛，各自独立用例。
- **入库验签**：验签失败的条目两列留空，且不阻断同包其余条目；同一包内「验签失败」与「验签通过」的条目共存时各自独立处理。

### 7.3 接口与集成

- `GET /v1/contributors` 无签名头亦返回 `200`。
- `POST /v1/profile`：合法昵称写入成功；超长 / 含控制字符 / 请求体带 `id` → `400`；缺签名头 → `401`；重放（同 nonce）→ `401`。
- 设置昵称后名册 `name` 随之变化；未设置时回退 `id` 前 8 位。

### 7.4 验收条件（AC）

1. 构造 12 个身份、各投不同数量且达门槛的内容 → 名册严格按规则返回前 10。
2. 把第 1 名的一条内容置为 `state='removed'` → 名册**实时**变化，其条数 -1。
3. 篡改某条目的 `author_sig` 后再入库 → 该条两列留空、不计入，名册其余部分**不受影响**。
4. 篡改 `contributors` 里某公钥后再入库 → 该 id 名下**所有**条目不计入。
5. 存量 `import-md` 内容（无归属）**不产生任何名册条目**。
6. 同一 `item_id` 连续重写 5 次 → 计数仍为 1。
7. 无签名头访问 `GET /v1/contributors` → `200`。
8. `POST /v1/profile` 请求体携带 `id` → `400`，且未写入他人昵称。
9. 两节点持有相同内容时，名册的 `id` / `count` / 顺序**完全一致**，`name` 允许不同。
10. `authorsig` 向量在 Go 与 TS 两侧**同时通过**。

## 8. 风险与留给后续册的开放项

1. **冷启动死锁（本册不解决，只标注）**：柔性名额解决了「新节点没有治理者」，但**没解决**「只有 1 个投稿人时 ≥2 人审批不成立」。第 3 册必须给出答案，可选路子：名册 < 2 时提案挂起（最纯），或允许节点运维方指定初始名册（代价：破例，不再是纯自治）。
2. **名册的域**：各节点持有的内容集合不同 → 名册不同 → 同一提案在不同节点判定不同。第 3 册必须明确「授权票绑定到哪个节点的名册」。本册只保证「持有相同内容 ⇒ 名册相同」。
3. **灌水未根治**：质量门槛只挡「空文章」，挡不住「200 字废话 × 100 篇」。真正的抗刷需要质量信号，而质量信号几乎必然是跨节点数据——与 §4.1 铁律冲突。若将来必须引入，**需先改总纲**。
4. **身份即贡献**：客户端自持密钥，换设备若未用密码托管取回私钥，贡献归零。这是模型的固有代价，不修。
5. **昵称的本地性**：`profiles` 不跨节点，用户在同一名册的不同节点上可能显示不同昵称、或缺名。若将来要求昵称全网一致，需引入「身份档案」跨节点机制——那是独立册子，不在本册。
6. **名册公开暴露 id 与条数**：id 是公钥派生的假名，不含身份信息；但不排除通过昵称与内容反推。本册不额外脱敏。
7. **`author_sig` 随内容版本重签**：条目内容一变，`content_hash` 就变，作者必须重新签名。第 2 册需保证「改写必重签」，否则更新后归属静默失效。

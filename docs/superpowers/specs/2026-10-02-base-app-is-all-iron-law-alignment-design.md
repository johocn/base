## 0. 一句话

铁律一要求「一套代码既是 App、又能当节点，节点部署在电脑或服务器上」，而 **Go 跑不了手机** ⇒ 收敛方向为 **TS 单核 + `Adapters` 缝隙 + Node.js 宿主壳**。既有总纲 §5.1 / §5.3 的「Go 单进程节点 + 双实现」是与铁律直接冲突的地基级表述，本册开列全部冲突并给出处置。迁移节奏已定案：**并行双跑，行为等价后 Go 节点退役**。

## 1. 三条铁律（最高约束）

以下三条为 2026-10-02 用户重设的开发目的，**优先级高于总纲与全部既有册子**。

### 1.1 铁律一：App 即全部

1. App 可以**独立存在**——离线可用、匿名可读、客户自持密钥，不依赖任何节点在线。
2. App 也可以**成为节点**；但**节点不在手机上**，要部署在**电脑或服务器**上。
3. 唯一自洽的读法：**同一份核心代码，两种宿主形态**（下称**同核双形态**）。
   - 手机宿主 = uni-app 壳（Android 优先）。
   - 节点宿主 = Node.js 壳（电脑 / 服务器）。
4. 推论（本册一切结论的根）：**Go 不能运行在手机上**，故协议层与业务核心必须是 **TS/JS 单实现**；现状的 Go 实现退化为**迁移期的并行实现**，等价后退役。

### 1.2 铁律二：跨设备 / 跨节点融合，只增不减

1. 内容可以**跨设备、跨节点融合**。
2. **融合动作只增不减**——增量合并与反熵**永不删除**。
   - 边界：本条**只约束融合动作**。删除仍可经票选 + 墓碑（含已登记的免票选删除），不受本条约束。
3. 融合时的**用户治理参照圈子的规则**；或**形成新圈子**。

### 1.3 铁律三：内容自治、票选原则

内容与内容的治理权归属于参与者，以**票选**为决断方式。

### 1.4 优先级与冲突裁决

1. 效力次序：**三条铁律 > 总纲 > 册子 > 计划 > 代码**。
2. 铁律之间冲突时：**铁律一（地基）> 铁律二 > 铁律三**。
3. 任何文档与铁律冲突，按 §4 处置矩阵处理；**禁止只改册子不改总纲**（总纲硬规则 1 不变）。

## 3. 收敛方向：TS 单核 + `Adapters` 缝隙 + Node 宿主壳

### 3.1 分层

```
packages/protocol-ts/       协议核（纯算法，宿主无关）—— Go internal/protocol 的 TS 单实现
packages/core-ts/  (新建)   业务核（store / peersync / packexport / importer 的 TS 单实现）
        ↑ 只依赖下列四个接口，绝不 import 'uni' / 'plus' / 'node:'
apps/mobile/src/platform/   Adapters 注入：uni-app 壳（现 adapter.ts 实现）
apps/node/src/platform/     Adapters 注入：Node 壳（新建）
web/                       节点门户模板 —— 随 Node 壳
cmd/based                  Node CLI 入口（迁移期与 Go 版并行运行）
```

### 3.2 迁移面（Go 包 → TS 落点，三级分类）

| Go 包 / 资产 | 职责 | 分级 | TS 落点 | 现状 |
|---|---|---|---|---|
| `internal/protocol` | canonical / sha256 / Merkle / Ed25519 / 签名 / manifest / author / reqsig / release / blobpack | **纯算法** | `packages/protocol-ts` | **大部分已有镜像**（含 `derivePackId`，见 `manifest.ts:54`）；**真缺口仅 `blobpack` 帧与 `ValidSlug`** —— 精确清单见 #70 §2 |
| `internal/markdown` | 解析 → 消毒 → HTML | **纯算法** | `apps/mobile/src/core/markdown.ts` | **已有**（三端同构，共享 `vectors/v1/markdown.json`） |
| `vectors/v1/*.json` | 14 组黄金向量 | **资产复用** | 同左 | 已符合；**单核后由「双侧消费」变「单侧消费 + Go 退役期继续消费」 |
| `internal/store` | SQLite 访问层（items / segments / blobs / govern_* / directory_terms / progress …） | **需平台适配** | `core/repo.ts` + `LocalDb` 注入 | 手机端已有同构的 SQL 仓储 |
| `internal/peersync` | 反熵 / 补齐 / scrub / 墓碑同步 | **需平台适配** | `core/sync.ts` + `core/entropy.ts` + `core/wire.ts` | 已有客户端半边 |
| `internal/packexport` | 导出内容包 | **需平台适配** | 新建 `core/packexport.ts` | 需新增（节点侧职能） |
| `internal/importer` | 本地导入器（md / video / quiz / course / category） | **需平台适配** | 新建 `core/importer.ts` | 需新增（节点侧职能） |
| `internal/httpapi` | 公开读 / 写 / 对端同步 / 审核路由 | **需平台适配** | Node 壳路由层 | 需新增（节点侧职能） |
| `internal/httpapi/tlscfg` | 节点间 mTLS / 指纹固定 | **宿主壳** | Node `tls` 模块 | 需新增 |
| `web/` | 节点门户（模板 + 少量原生 JS，内嵌） | **宿主壳** | Node 静态模板 | 需新增 |
| `cmd/based` | CLI：serve / import / export / release / scrub / peer-sync / tlscert | **宿主壳** | Node CLI | 需新增 |

> 三级口径：**纯算法**＝可近乎逐行直译；**需平台适配**＝逻辑通用但依赖 DB / FS / HTTP，靠 `Adapters` 注入；**宿主壳**＝本质是进程、监听、CLI，Node 壳用原生能力重写。

### 3.3 Node 宿主壳

- 复用同一个 `Adapters` 接口，实现 `NodeFs` / `NodeStorage` / `NodeHttp` / `SqliteLocalDb`（Node 侧 SQLite 驱动）。
- **目标态**：手机壳与 Node 壳加载**同一份 core**，差异只在壳。
- 节点**不是权威，是登记与缓存**（总纲 §1 不变）；同核双形态不改变节点职责，只改变节点由谁实现。

### 3.4 迁移节奏（已定案）

**并行双跑 → 行为等价后退役 Go。**

1. TS 核心先接管手机端读写（现状已是）。
2. Node 宿主壳上线，与 Go 节点**同时在线**，同一份数据面互相比对。
3. 行为等价（接口响应、哈希、签名、反熵结果逐项一致）后，Go 节点进入只读，再退役。
4. 迁移期「双实现」是**有意的临时状态**，不写入目标态描述。

## 5. 正文存储形态：base64 决策

**结论（已定案）：不做正文的默认存储形态，只做自携带导出。**

| 项 | 判定 |
|---|---|
| 正文默认存储 | **保持现状**：sha256 内容寻址 + `blobs` 表去重，正文走 `attr.body_md` 源文本 |
| base64 的位置 | **只有一处**：单条内容的导出 / 分享，作为自携带形态（拷到哪都能看） |
| 不做 | 不把正文内联 base64 落库；不改内容包规范 v1；不 bump `schema_version` |

三条理由：

1. 「融合只增不减」下 base64 膨胀**不可逆**（同一条内容 base64 化后再去重，哈希已变）。
2. `blobs` 表 sha256 内容寻址是这套追加式系统**唯一的去重机制**；内联会绕开它，秒传 / 副本因子 / 反熵 / Merkle 清单五项随之失效。
3. 手机端**已能**消费 pack 并落盘 blob（`core/blob.ts` + `Adapters.packReader`），协调层是现成的，无需换形态。

**登记**：`data:` 目前是渲染层明确丢弃的危险向量（`vectors/v1/markdown.json` 覆盖该项），若日后要做自携带导出，**须另开册子**并同步该向量。

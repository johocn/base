# base 业务卡点审计与排期（影响 × 成本矩阵）

- 日期：2026-11-08
- 状态：设计定案（待实施；三批次另出计划）
- 上游：总纲 `2026-09-25-base-distributed-learning-design.md`、全部册子（`docs/README.md` #1–#82）
- 定位：**一次横向体检**，不是新功能设计。回答一个问题：现有能力已经很长，为什么用户仍然频繁卡住？结论是**送达与验证闭环缺失**，而非功能缺失。

## 0. 背景与结论

### 0.1 取证范围

| 来源 | 用途 |
|---|---|
| `docs/README.md` #1–#82 | 已落地能力、待人工验收欠账、明确不做的边界 |
| `git log` 近 35 条 | 近期真实返工点（R2 spike 8 连修、mesh 取 IP 3 连修、版本号错漏） |
| 源码扫描 | `TODO/FIXME` 零命中；`removeBlob` 只用于编辑替换；`search.ts` 注释自认全表扫描 |
| 真机反馈（2026-10-18 ~ 11-08） | 入口看不到（两次）、下载页指旧包、IP 取不到（三次）、邀请码无处可查 |

### 0.2 总判断

**功能面不是主要矛盾。** 27 个页面、12 个已落地册子、四 workspace 全绿，说明「做功能」这条路是通的。
**主要矛盾是「改完无法可靠送达并证明有效」**：发布三处靠手工、验收长期欠账、诊断入口缺失。任何一处漏改，用户侧表现都是「这个功能不存在」。

## 1. 方法：四维评分与准入规则

### 1.1 维度定义

| 维度 | 含义 | 取值 |
|---|---|---|
| **L 用户损失** | 出问题时的可感知代价 | 5 = 功能不可用或数据错误；3 = 体验受损、需绕过；1 = 仅困惑 |
| **P 事故概率** | 多大概率撞上 | 5 = 已实际发生；4 = 结构性必现；2 = 偶发；1 = 理论 |
| **C 改动面** | 修复要动多少层 | 1 = 单页 / 单文件；2 = 单 workspace 内几处（或加一个脚本）；3 = 跨 `core-ts` + 前端；4 = 跨 `core-ts` + 前端 + 数据库 schema / 迁移；5 = 涉协议 / 节点 / 黄金向量 |
| **V 可验证性** | 修好后能否证明 | 1 = 有自动化门禁；3 = 只能人工清单；**5 = 无手段验证** |

### 1.2 准入规则（写死）

1. `L + P ≥ 7` 才有资格进 P1 及以上（低于 7 直接落 P2）。
2. **P0 需同时满足三条**：`L + P ≥ 9`、`P = 5`（已在真实用户身上发生）、`C ≤ 2`（本周内可修）。三条缺一即落 P1。
3. **P0 / P1 一律要求 `V ≤ 3`**；`V = 5` 的项目不得进前两档，必须先补验证手段（或改为「设计先行」进 P2）。
4. 分档含义：
   - **P0 止血**：正在流血，本周内修。
   - **P1 收口**：本阶段内做完，紧随 P0。
   - **P2 立项**：单独立册排期，不合并施工。
   - **P3 不做**：已定边界，写死不重开。

规则 3 的由来：近场取 IP 连续三版返工，根因正是「没有验证手段就动手」——每版都靠用户截图反馈才知道失败。把「可验证性」做成准入硬门槛，是本次审计最重要的方法论产出。

## 3. 三批次与闸门

### 3.1 批次一 · 止血（P0）

**做**：
1. 发布一致性校验一条命令：**落地页下载链接、`/v1/release` 版本与 `min_version`、APK 文件名与 sha256** 三者互校，任一处不一致即非零退出。
2. 版本号强制校验：`pages.json` 与 `manifest.json` 的 `versionName` / `versionCode` 必须一致且单调递增，脚本校验。
3. 生产线切版：`release.json` 与落地页同步到当前开发版（0.21.11 / 54），验收包与生产包不再并行。

**闸门**：脚本在「故意改错其中一处」时能报错；生产线与开发线版本差 ≤ 1。

### 3.2 批次二 · 收口（P1）

**做**：
1. 自检页新增「网络出口 + mesh 端口 + token 状态」诊断项（把 `share.vue` 已有的诊断能力复用上去）。
2. IP 自动探测收口：以真实热点 / 同 Wi-Fi / 纯流量三场景为准，达到**不手填也可用**；手填保留为兜底而非主路径。
3. 存储占用可见 + 一键清理（清块、清 gossip 收件、清待发队列，分项显示大小）。
4. 六个册子与 #82 的真机清单合并为**一份可勾选验收表**，逐条有结论。
5. 最小 CI：`npm test` + `npm run typecheck` + 发布一致性脚本，在推送 / PR 上自动跑。

**闸门**：真机清单全部有 `PASS/FAIL` 结论（不允许留空）；CI 在 PR 上跑绿且失败会阻断合并。

### 3.3 批次三 · 立项（P2）

各自独立开册子，**不合并施工**：
- 灰度与回滚（`release.json` 加 `staged`/`rollback` 语义）。
- 圈子随码分发（新增签名对象，不允许改 `mesh-catalog` 形状）。
- 快照降级（pack v1 容器零扩展，rev 只进不退）。
- ② 类断网可用性（先设计再动手，不得为可用性牺牲密钥分发安全）。
- 搜索优化（倒排或索引表，需先定内容量阈值）。

**闸门**：每册子各自出计划，各自过门禁，不设统一截止日。

### 3.4 P3 边界（写死，不重开）

- 息屏保活（R2 硬死路）
- iOS 做源端
- mDNS / UDP 设备发现
- ② 类内容互传（M1 一期写死）

## 4. 不做什么

- 不改内容包规范 v1、不 bump `schema_version`。
- 不自定义抽象、不新增配置项（除发布脚本必需的参数）。
- 不重构既有可运行模块；本册只读与只排期，P0/P1 的改动按各自计划执行。
- 不把 P2 的内容塞进批次一、二。

## 5. 验证方式

| 批次 | 验证形态 | 判定 |
|---|---|---|
| 一 | 脚本自测（故意注入三处不一致） | 全部非零退出 |
| 一 | 公网探活 | 落地页 / `/v1/release` / APK 三处版本与哈希一致 |
| 二 | 真机清单 | 每项有结论，无空项 |
| 二 | CI | PR 上跑绿；注入一处失败能阻断 |
| 三 | 各册子自有 AC | 按册执行 |
